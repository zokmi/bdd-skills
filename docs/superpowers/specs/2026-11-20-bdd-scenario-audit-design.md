# 既有 BDD 情境合規檢查

## 目的與範圍

新增 `skills/bdd-scenario-audit/SKILL.md`，供使用者檢查既有 `.feature` 是否符合本插件目前規範。這是靜態文件審查，不代表產品實測通過。

使用者追加要求：新增或異動情境文件後自動使用未參與撰寫的子代理檢查，包含刪除、改名、整併及影響情境的 MODULE.md 異動。以相關修改完成為派工單位，必修修正後複審。可與既有獨立情境審核合併派工，分別記結論；無代理則阻塞。這是代理工作流程關卡，不實作外部編輯的檔案監聽。

預設唯讀：不修改情境、不執行 UI／API／DB、不啟動服務、不更新 issue。使用者指定檔案或模組時依其範圍，未指定時盤點 repo 的 `.bdd/modules/`；舊格式另列，不自動搬移。後續修正須有使用者指示。

## 方案與建議

1. 擴充 `bdd-local-test`：共用入口，但容易觸發環境確認、實測派工及交付流程。
2. 新增獨立 `bdd-scenario-audit`（建議）：明確區分文件合規與實測，引用現有撰寫及模組規範，避免重複維護規則。

## 檢查內容

- 情境是否描述角色可觀察的業務行為，包含 UI、外部 API、事件與排程；工程調整應另列技術驗證。
- 前置條件、操作或觸發、成功與適用異常結果是否清楚可判定，有無重複、矛盾、照抄錯誤實作。
- 檔頭、模組歸屬、編號、標籤與測試資料命名是否符合既有規範；適用規則須有依據。
- 需求來源可得時檢查覆蓋；來源不足則列待確認，不憑程式或猜測新增需求、也不宣稱完整合規。

可先執行既有 `bdd-modules.ps1 -Lint` 做格式檢查，再做語意審查；lint 通過不等於業務覆蓋完整。只讀必要參考文件，不啟動 bdd-local-test 的完整實測流程。

## 產出與驗證

回報範圍與規範版本、合規結論（PASS／FAIL／待確認）、問題表（嚴重度、檔案行號、情境編號、規範依據、修正建議）、需求覆蓋限制。未取得充分需求時只能就已檢查項目下結論。預設於對話輸出，指定報告檔時才寫檔。

以案例驗證：工程調整混入情境、缺少異常路徑、合法外部 API／排程、需求不足、lint 通過但結果不可判定。同步 README 發現入口，不改版本、不發布或安裝。
