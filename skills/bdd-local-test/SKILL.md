# BDD 情境與本機驗證

將需求寫成可判定的情境，實際執行並保存證據。產品缺陷要修正、重啟受影響服務並複測；無法解除的阻塞如實回報。情境存於 `.bdd/modules/<portal>/<主路由>/`；每輪的 `REPORT.md`、`verification.json` 與證據存於 `.bdd/<單號>-<主題>/`。使用者指定其他範圍或只要情境／報告時，依其要求縮小流程。

## 共同規則

- 先讀目標專案的 `AGENTS.md`／`CLAUDE.md`／README、環境設定及 `.bdd/config.json`。本 skill 不預設埠號、帳號、基準分支或資料庫。下文的 `<skill 目錄>` 是此檔所在資料夾。
- 依 [版控分工](references/version-control.md)，Git 只保存模組情境、`MODULE.md` 與共用設定；每輪報告、驗證與遮罩紀錄及證據保存在本機輸出與完整封存，不新增到 Git、不另建純報告提交。既有追蹤輸出先驗證封存，再依明確授權遷移。
- 「那麼」以需求為準，不照抄錯誤實作；發現不符時標 `@已知缺陷`，實測讓它失敗。只有走真實路徑驗到的結果才能記「通過」；模擬回應、假 token 或旁證不能代替端對端驗證。
- 報告只對記錄的 repo、commit 與工作區狀態有效。同步或受測檔案變更時先用 `bdd-verification.ps1 -Check` 判定；`rerun` 代表舊結果失效，完整重跑的時機依下節驗證階段決定，不在合併前後各跑一輪。
- 執行可能寫入資料前，確認連到本機或使用者已確認的測試環境；SIT／UAT／PROD 或無法判定時停止寫入並詢問。缺帳密時不得繞過驗證，相關情境列「阻塞」。
- 情境新增或修改後先跑 `bdd-modules.ps1 -Lint`，再按 [情境審核](references/scenario-review.md) 做獨立審核。情境審核子代理只讀原始需求與程式，不修改檔案；審核問題逐條處理。
- 每輪實測前依下節判定執行模式；可拆成至少兩組安全獨立執行的情境且有可用子代理時，自動派實測子代理，不等待使用者說「並行」。情境審核、實測派工與 issue 前一致性審核是三個不同步驟，完成其中一項不代表完成其他項。
- 截圖當下遮蓋個資並登記；未遮罩的證據不得上傳或封存。全通過表示失敗、阻塞、未執行皆為 0，且每個情境都經真實路徑驗證。
- BDD 全通過後要更新 issue 時，先依當下 issue、repo、commit 範圍與可用 skill 動態選擇唯讀一致性審核 skill；Redmine 且需要需求／程式雙向比對時優先選 `issue-code-consistency-check`。派子代理審核結果只有 `PASS` 才能寫入 issue，其他結果一律阻擋並回報。Redmine 註記逐項使用「修正項目 N」後緊接「圖片 N」，純 API／DB 情境改附替代證據。
- 用檔案編輯工具寫 `.feature` 與 `REPORT.md`；內容常含引號與反引號，避免用會被 shell 解析的 heredoc。

## 按階段讀取

### 先決定驗證階段，再派工

進入本機實測前就讀 [整合與封存](references/closeout.md)〈7-0〉，確認本任務已指定的交付方式，不等到收尾才讀。每次派工明列「開發回饋／最終完整驗證」及情境清單：

| 目前狀態 | 本輪驗證範圍與下一步 |
|----------|----------------------|
| 合併回 develop，尚未整合 | 只驗修正與受影響回歸，通過後提交並進入整合；不為取得 all pass 預先全跑。 |
| 交付方式未定 | 先驗修正與受影響回歸，通過後詢問交付方式；回答前不自行開完整驗證。 |
| 已選 feature 或明確只要實測報告 | 在功能工作區完成指定範圍的完整驗證。 |
| develop 候選整合已完成 | 在乾淨候選 commit 完整驗證一次，通過後推送同一 HEAD；推送後只核對遠端 SHA。 |

`rerun`／`no-record`、子代理自動分組與「測到全部通過」都不改變上述時機。開發回饋所需情境若恰好等於全部情境，照實執行並記範圍；不能省掉必要回歸，也不能把它當作尚未完成的整合驗收。若使用者明確要求整合前完整測試，依要求執行並說明整合後仍須驗證新版本。

### 每輪實測的執行模式判定

初測、缺陷修正後複測、`rerun`、feature 完整驗證與整合後驗證，都在既有執行時機先判定一次；只產情境或整理既有報告而不實測時不派實測代理。此判定不額外增加測試輪次。

1. 主代理確認本輪情境、受測版本、環境安全與可用子代理名額，按模組、依賴、資料與瀏覽器衝突分組，不以情境數硬切。
2. 可安排至少兩組獨立執行、且有可用子代理時，先讀 [子代理並行 BDD](references/parallel-bdd.md)，建立派工契約後實際派工；名額不足以同時啟動所有組時分批執行。使用者只說「測到全過」「複測」或「只給報告」也適用，不另問是否要用子代理。
3. 只有部分組衝突時採混合模式：衝突組序列執行，獨立組仍派工。只有一組、全部相互依賴、無子代理工具／名額，或使用者明確禁用時，主代理序列執行並記錄具體原因。不得為湊組拆開有順序依賴的單一情境，或為啟用並行改用假資料／繞過環境確認。
4. 執行前簡述所選模式及分組依據，寫入報告〈BDD 執行模式〉；派工後記錄實際代理與契約位置。子代理本身不遞迴派實測代理，只執行主代理分配範圍；需要再拆組時回報主代理。

情境獨立審核仍依原流程執行，不由執行該組的代理自行審核。使用者明確要求子代理時，在安全與工具限制內遵守；無法派工時回報具體限制，不假稱已派工。

1. **確定範圍、版本與情境**：讀 [範圍、版本比對與情境撰寫](references/workflow-and-scenarios.md)。寫 `.feature` 前讀 [情境寫法](references/feature-guide.md)；使用模組時讀 [模組情境集](references/modules.md)。情境寫完後讀 [情境審核](references/scenario-review.md)。使用者只要情境時，在審核與未執行報告完成後停止。
2. **本機實測與修正**：需要執行時讀 [本機執行與複測](references/local-execution.md) 及 [報告與驗證紀錄](references/reporting.md)；worktree 另讀 [loopback 隔離](references/worktree-loopback.md)。逐情境保留證據，每輪先記錄結果與版本；失敗後修正、重啟並重測。
3. **報告**：需要報告時讀 [報告與驗證紀錄](references/reporting.md) 和 [報告範本](assets/REPORT-template.md)。使用者只要測試報告時不整合或更新 issue；若需封存，再讀下階段的封存步驟。
4. **整合與收尾**：讀 [整合與封存](references/closeout.md)。worktree 開發與相關回歸通過後，未指定交付方式時自動詢問「轉為正式 feature 分支／合併回 develop」，不等使用者要求收尾；本任務已指定時沿用。合併模式開發中只測修正與相關回歸，於最新 develop 候選整合後、推送前完整驗證一次，推送後只核對 SHA，再完成已授權的 issue 更新與封存；feature 模式先在功能 worktree 完整 BDD 通過，確認名稱後才轉換分支並保留工作區，僅改名且版本與環境未變不重測。未回答前不轉換分支、合併、推送或刪除證據／worktree。只要情境或報告的明確要求依限定範圍完成，不列為第三個開發交付選項。服務停止獨立依收尾指引的共用條件判定，不等待模式選擇或封存。遮罩、封存或清理時再讀 [封存指引](references/archive.md)。

各階段只讀當前需要的參考文件，不把整套參考文件一次載入。腳本的參數、輸出與錯誤處理以對應階段文件為準。

合併模式的完整驗證時機依 [整合與封存](references/closeout.md) 執行；rerun 集中在整合後、推送前，不在整合前多跑一輪。current／still-valid 未涵蓋所有共用程式與環境，不能代替整合驗證。
