# BDD 測試登入

通過資料庫環境確認並核對實際 UI、API 與受測版本後，按情境需要的測試帳號與角色準備登入。登入、登出、匿名存取或切換身分本身是驗收目標時，依情境要求從乾淨的隔離 session 開始並實際執行該步驟。平行組仍遵守各自的帳號、MCP session 與資料範圍。

1. **先重用登入。** 同一組在已連線的 MCP session 中可沿用已確認的身分。新 session 優先找專案指定的 Playwright storage state。專案未指定位置時，在 Windows 使用目前使用者的 `%LOCALAPPDATA%/bdd-skills/auth/<識別鍵>.json`。以 UTF-8 JSON 陣列的 SHA-256 作為識別鍵，固定順序放入 Git common directory 的絕對路徑、前端有效 origin、API 有效基底 URL、已確認的環境及資料庫目標、租戶、角色、測試帳號別名。各欄位須能明確對應，否則只沿用本輪 session。主機或有效埠改變就重新準備登入，不改寫快取內的 origin 或 cookie。不同 worktree 即使命中同一份檔案，也要獨立匯入，且並行時須先確認同帳號不會互踢或共享可變伺服器狀態。
2. **匯入並驗證。** 新的隔離 MCP 可用 `prepare-worktree-mcp.ps1 -StorageState <檔案>` 並照回傳的 `server.command`／`server.args` 啟動。已連線的專用測試 session 若有 `browser_set_storage_state`，可直接匯入後重新導覽。用專案受保護頁面或身分端點確認確實是預期帳號、角色與租戶。登入頁、401、權限或身分不符時，捨棄該 session 並用乾淨的 session 走下一步。MCP 缺少匯入能力時直接走下一步。
3. **自動重新登入。** 優先使用專案已提供的測試登入命令、fixture 或官方登入端點，從指定秘密來源在程序內讀取憑證。若專案提供 UI 表單及秘密注入方式，用 Playwright MCP 操作真實表單。憑證值不得傳入會回顯或留下明文的工具參數、命令列、日誌或證據。UI 驗證需在同一個 MCP 瀏覽器取得可用的登入狀態；僅取得 API token 時可用於核對後的 API 請求。重新驗證預期身分後再開始測試。自動登入失敗時先查明原因，避免反覆送出憑證造成鎖定。
4. **只在需要時請人登入。** 沒有可用的合法憑證注入方式，或登入要求本人完成 MFA、CAPTCHA、互動式 SSO 時，請使用者在本輪專用瀏覽器完成所需操作。等待期間先執行獨立情境。使用者完成後，仍須用受保護頁面或身分端點核對身分，並繼續原本的測試。無法取得身分的情境列為阻塞。
5. **儲存已驗證的狀態。** 用 MCP 的 `browser_storage_state` 或在同一個 MCP context 呼叫 `page.context().storageState({ path })`，只回傳成功狀態，不回傳內容。先寫入使用者私有目錄的唯一暫存檔，再由本組管理者原子替換自己的快取檔，平行組不得覆寫彼此的狀態。瀏覽器所在主機與載入端須能存取同一份私有檔案。依賴 sessionStorage 或無法序列化的驗證方式時，沿用同輪 session 或走專案登入流程。報告只記錄登入來源、角色及結果，狀態檔與 token 不放進 repo、BDD 證據、封存或附件。
