# BDD 版控分工

Git 保存持續維護的規格；每輪執行結果由完整封存包保存。維持現有 `.bdd/<單號>-<主題>/` 輸出路徑，不改腳本介面。

| 項目 | 保存方式 |
|------|----------|
| `.bdd/modules/**/*.feature`、`MODULE.md` | Git，隨程式修改提交 |
| `.bdd/config.json` | Git，僅限共用設定；帳密與個人路徑不提交 |
| `.bdd/<單號>-<主題>/` 全部內容 | 本機輸出及完整封存，包含報告、驗證紀錄、遮罩紀錄、截圖、log 與瀏覽器 profile |
| 封存 ZIP 與 `index.jsonl` | repo 外封存庫；已授權時上傳 issue |

## 白名單判定

本規則限定專案的 `.bdd/`，不排除插件本身的腳本、範本、文件與測試。採「路徑＋用途」白名單；檔案小、純文字、已遮罩或副檔名為 `.feature` 都不是例外。

- `.bdd/modules/` 只允許持續維護的 `.feature` 與 `MODULE.md`，不得放入報告、log、截圖或實測資料。情境使用虛構資料或參數，不寫入真實姓名、帳號、密碼、token 或 OTP。
- `.bdd/config.json` 只保存無敏感資料的團隊共用設定；個人封存位置改用參數或環境變數。
- 單號目錄內的 `.feature`、`REPORT.md`、`masking.json`、`verification.json`、PNG／PDF、API log、資料庫紀錄、唯讀盤點 SQL 及協調 JSON 全部屬於本輪輸出，不提交。
- 需要長期維護的情境先整理到對應模組；可重用的測試工具或 SQL 放到專案既定的工具／測試來源目錄，移除實測資料並經程式審查，不以搬移路徑規避規則。

## 忽略規則

每次開始 BDD、切換 repo/worktree 或整合分支後，建立輸出前執行：

```powershell
pwsh -NoProfile -File "<skill 目錄>/scripts/ensure-bdd-gitignore.ps1" -Repo "<git 根目錄>"
```

預設用 Git 實際忽略結果驗證預期路徑及現有 `.bdd` 檔案；缺漏時在根目錄 `.gitignore` 附加有標記的規則區塊，保留原始內容，已符合規範則不修改。整個 `.bdd/` 被忽略時會補上父目錄放行規則，讓 Git 能遍歷 modules。重跑不重複新增。`-Check` 僅檢查，適合 CI 或專案明確禁止自動修改時使用。

JSON 的 `failures` 提供路徑與匹配規則，`trackedOutputs` 列出已追蹤產物；exit 0 = 通過、1 = 缺漏或已追蹤產物、2 = 執行錯誤或規則衝突。巢狀規則導致補齊後仍不符合時還原本次修改；既有管理區塊失效時停止並回報，先查明衝突。不修改巢狀／全域規則、不自動停止追蹤、不刪除產物。已追蹤資料依下方遷移流程處理。

依專案規範更新 `.gitignore`；已有明確相反規範時先回報差異，不自行覆蓋。建議以預設排除、明確保留的方式避免新增執行產物誤入版控：

```gitignore
/.bdd/*
!/.bdd/modules/
!/.bdd/config.json
/.bdd/modules/**/*
!/.bdd/modules/**/
!/.bdd/modules/**/*.feature
!/.bdd/modules/**/MODULE.md
```

檢查模組子目錄沒有被其他規則忽略，並以 `git check-ignore -v --no-index <路徑>` 核對報告被排除、模組情境及共用設定可追蹤。若專案整個忽略 `.bdd/`，需先調整父目錄規則才能保留 modules；不要用 `git add -f` 繞過。

提交時明列本次程式、模組情境與共用設定路徑，不使用 `git add .` 收進執行產物。不為服務停止、issue 上傳或封存結果另建純報告 commit；受測版本以程式與情境 SHA 記錄。

## 提交與合併檢查

提交前查看 `git diff --cached --name-status -- .bdd/`；合併前分別查看來源與目標的 `git ls-tree -r --name-only <ref> -- .bdd/` 及待合併 diff；整合後用 `git ls-files -- .bdd/` 再核對。除白名單外的新增、修改或仍被追蹤檔案須先處理；經授權停止追蹤產生的刪除項目可作為遷移提交。

檢查涵蓋來源分支已有、目標分支原有與合併新增的輸出，不能只看本次新增檔案。main 與 develop 都須符合相同白名單；授權涵蓋兩條分支時，以同一遷移提交合併或 cherry-pick 後逐支核對。授權只涵蓋單一分支時，列出另一分支的待處理項目，不宣稱兩邊已一致。規則生效前已提交的檔案仍須依下節遷移。

## 已追蹤輸出的遷移

`.gitignore` 不會停止追蹤既有檔案。先確認指定輸出的完整 ZIP 已建立、雜湊驗證成功且可還原；合併收尾模式還須確認 issue 附件可下載。尚未完成時保留原始資料。

有明確遷移授權後，列出 `git ls-files -- .bdd/<單號>-<主題>/`，只對核對過的輸出路徑使用 `git rm --cached -- <檔案>`，保留本機內容。不要遞迴移除整個 `.bdd/`，不要改寫歷史。停止追蹤的刪除項目與 `.gitignore` 為一次性遷移提交；其他 repo/worktree 不自動遷移。

未授權遷移的已追蹤報告保留在工作區，不自動提交其更新、不丟棄異動。若因此無法取得乾淨整合工作區，回報待遷移項目；不能將它夾帶進程式提交或強行清理 worktree。

`git rm --cached` 只讓後續版本停止追蹤，既有 commit、tag 與歷史內的二進位檔仍在；不能宣稱已清除敏感資料或縮小 clone。來源 commit 即使尚未推送，若以一般 merge 納入其歷史後推送，產物仍會進入遠端歷史。若要求「從未進入遠端歷史」，先核對遠端 refs、待推送 commits 與 tags，提出具體重建／改寫範圍；另取得明確授權後才處理，不自動 reset、rebase、刪 tag 或 force push。

## 複測與保存

`verification.json` 仍須逐輪產生；情境仍需先 commit，封存腳本才能從受測 SHA 取出快照。限定報告任務保存本機輸出，使用者要求封存時才封存，不額外上傳。團隊共用結果以已確認可下載的 issue 附件為入口；本機封存路径不能充當團隊可用連結。
