# 本機執行與複測

開始操作前讀取本 worktree 的 `.bdd/config.json`。優先使用內建轉送、createApi 與已啟用的 createDb。工具缺少情境能力時才寫本輪腳本。參閱[內建實測工具](test-kit.md)。

**先決定本輪範圍，再執行情境**。依[分階段工作流程](execution-workflow.md)區分開發回饋與最終完整驗證。已選合併模式時，先驗修正與受影響回歸，在候選整合後完成本輪全部必測項。`rerun`／`no-record` 只使舊結果失效。若已授權回寫 issue 且分支模式未定，先在當前 worktree 驗證本單開發範圍並完成階段回寫。「Issue 回覆內容審核」通過後完成受影響的回歸，再依[收尾模式](closeout.md#7-0-確認收尾模式)停止本輪服務並詢問需要的分支選擇。

每輪實測先完成 `SKILL.md`〈每輪實測的執行模式判定〉；確認版本與本節環境安全後，兩組以上可獨立執行且有子代理名額就依 [子代理並行 BDD](parallel-bdd.md) 自動派工。初測、修正後複測及同步／整合後重跑都適用；情境沒改只是不重做情境審核，不免除實測分組判定。無法並行的範圍序列執行，其他獨立組照常派工。

### 4. 執行前的安全確認

開始實測或派實測子代理前，核對本輪清單已取得[實測範圍審核](execution-workflow.md#實測範圍審核) PASS，並完成下列環境確認。

**必須取得使用者對具體資料庫環境的明確確認，才能開始實測。本機與唯讀情境同樣適用。** 順序如下：

1. **盤點實際目標**：讀前端 API 位址、後端生效的連線設定、啟動 profile、環境變數與覆寫來源，列出所有資料庫主機／執行個體、埠（如有）、庫名、租戶（如有）、環境用途、設定來源及本輪讀寫範圍。不輸出密碼、token 或完整連線字串。API 在 localhost、庫名含 Test／Dev 或設定寫 Development 都不能代替確認。未知目標先補齊，不能當作已確認。
2. **展示並詢問**：例如「本次 API 為 http://localhost:5000，實際資料庫為 (localdb)\\MSSQLLocalDB／App_Test，環境 Development，來源為啟動 profile 與連線設定；測試會新增、修改及清理本輪測試資料。請確認這是正確的測試資料庫，並同意在此環境執行本次 BDD。」依實際情境說明唯讀或寫入範圍，多資料庫逐一列出。
3. **等待明確回覆**：收到使用者針對上述目標表示「確認／正確，可以測試」才解除關卡。只告知、已送出問題、選項預選、逾時、沉默或使用者只說「開始測試／直接跑／測到全過」均不算資料庫確認。回覆含糊或否認時先釐清。
4. **確認前不實測**：可讀本機文件／程式／設定、撰寫與審核情境、整理計畫；不可執行 UI／API／DB 情境（含唯讀查詢）、登入、seed、migration、清理資料或啟動可能連庫自動寫入的服務，也不可派實測子代理。子代理缺確認證據時回報主代理等待使用者，不先跑唯讀情境。無法取得確認時列「阻塞：待使用者確認資料庫環境」，不宣稱通過。
5. **記錄與沿用**：報告〈資料庫環境確認〉記錄目標清單、環境、設定來源、讀寫範圍、確認回覆摘要、對話位置／時間（可取得者）及適用輪次。證據須來自使用者；設定檔、舊報告或代理自行宣告不算。同一任務目標與授權範圍未變的複測沿用已取得的明確確認，每輪仍核對設定；主機、執行個體、埠、庫名、租戶、環境或讀寫範圍變更，以及跨 repo 時，停止並重新展示、取得確認。只改 worktree 或版本且目標與範圍未變，不重複問。

環境確認不授權清除未知歸屬資料、全表 DELETE／TRUNCATE 或超出確認範圍的操作。SIT／UAT／PROD 須清楚揭露實際環境與影響，依專案限制執行，不自行改稱開發測試庫。

- 從專案文件指定的秘密來源取得測試帳密，或在缺少可用狀態及登入方式時，請使用者完成登入。**不要猜、不要寫進 `.feature` 或報告**（報告只寫「以具備 X 權限的測試帳號」）。
- **沒有帳密時，不要繞過驗證**：不自己建帳號、不把帳號加進管理員群組、不用設定檔裡的金鑰自簽 token、
  不改權限資料。這些動作在共用資料庫留下的是一個真的能登入的高權限帳號與稽核紀錄，
  而且測出來的結果也不代表真實使用者的權限路徑。需要登入的情境標「阻塞」，寫明要什麼權限的帳號才能解除。
- **寫入刪不掉的資料要先想清楚**：有些表受觸發器或稽核規則保護，寫進去就刪不掉（例如價格版本、簽核紀錄）。
  驗證這類約束時，把寫入包在交易裡、驗完回捲；需要留下資料才能驗的，先問使用者。

### 5. 準備環境

範圍審核與環境確認完成後，依[並行準備服務與測資](parallel-bdd.md#並行準備服務與測資)派工。下列環境準備由服務子代理負責，已核對的就緒資訊交給測資代理及適用的實測代理。

依核准清單查出所需服務的原始 URL、設定來源、啟動命令及適用的 proxy／SSR 上游。worktree 自動隔離，多專案主 checkout 加 `--isolate`。各組共用本輪服務管理者交付的 IP 與有效埠。整輪只需 API 時，管理者可用 `node bdd.mjs loopback-slot --ports <API 原埠>` 取得對應。純 API 組直接核對服務版本、真實身分及資料範圍；瀏覽器及路由探測僅在操作或必要前置需要 UI 時準備。

`@UI` 的前置套件為 Node.js 20 以上與 Microsoft 的 `@playwright/cli`。以 `npm install -g @playwright/cli@latest` 安裝，再用 `playwright-cli --help` 確認命令可用。若 `open` 回報缺少瀏覽器，依錯誤訊息以 `playwright-cli install-browser <瀏覽器>` 安裝本輪設定使用的瀏覽器，再重試。[官方安裝與命令說明](https://github.com/microsoft/playwright-cli)

**本輪需要 UI 時**，依 [worktree 隔離](worktree-loopback.md) 執行 `node bdd.mjs prepare-worktree-cli --ports <原埠清單> --output-dir .bdd/.playwright-cli/<本輪-組別>`，保存回傳的 `portMappings` 與 `effectivePorts`。一般單專案主 checkout 沿用專案的 localhost 流程。在本輪暫存目錄建立 CLI 設定 JSON，將 `outputDir` 設為該組暫存目錄的絕對路徑，從受測 checkout 執行 `playwright-cli -s=<名稱> open --config="<設定檔>"`。CLI 會自動保存可能含帳號或畫面內容的 snapshot 與日誌；各組使用 `.bdd/.playwright-cli/<本輪-組別>/` 或私有暫存目錄，與報告、`evidence/` 和封存來源分開。僅保留核准的遮罩證據，測試收尾時清理本輪 CLI 暫存檔。

- 依本輪有效埠啟動服務。需要前端時設定 API／proxy／SSR。隔離工作區的 UI 組使用[專用 CLI 工作階段](worktree-loopback.md#啟動專用-cli-工作階段)，在路由探測通過後以同一個具名 session 導覽應用頁面。
- Node 專案若在 `npm run build` 時報埠號占用，檢查 `package.json` 的 `prebuild`、`build`、`postbuild` 及它們啟動的子程序。純建置可並行。啟動 dev server、preview 或 SSR 的命令須使用本輪有效埠；若流程可拆開，先完成 build，再以有效埠啟動提供建置產物的服務。建置時若會連到 API 或把 API URL 寫入產物，也要在建置程序中套用本輪 API 目標。
- 核對受測服務的實際監聽位址、程序歸屬、版本及 HTTP 回應。UI 有呼叫 API 時也須確認請求進入本輪版本。若需要另起服務，從包含本輪待測異動的工作區建置，避免測到舊版本。缺少上述證據時，相關情境列為阻塞。
- 報告記錄原 URL、原埠與有效埠、占用判定、實際 UI／API 網址及版本證據。清理時使用同一輪記錄的有效埠。
- 啟動失敗、缺帳號、缺資料庫權限 → 相關情境標「阻塞」並寫明原因，其餘能跑的照跑，不要整批放棄。

### 6. 逐情境執行

需要已登入身分的情境，先走 [登入自動化](authentication.md) 並確認真實帳號與角色。登入、登出及權限本身是驗收目標時，依情境明確建立初始狀態並實際操作要驗證的步驟。

依核准清單中[各斷言的手段](feature-guide.md#逐項選擇驗證手段)執行。混合情境由同一組完成原訂操作，依各列取證。API 可驗的服務端邊界可直接呼叫真實端點；要求實際點擊或觀察畫面的列使用 Playwright CLI。

| 標籤 | 手段 | 證據 |
|------|------|------|
| `@UI` | 在受測工作區用同一個 `playwright-cli -s=<名稱>` 執行 `goto <受測網址>`、`snapshot`，再依最新畫面的元素 ref 執行 `fill`、`click` 等真實操作。用新的 `snapshot` 或 `run-code` 的 locator 斷言核對結果。共用 session 的操作依序執行 | 記錄實際操作、預期與觀察結果，依核准的清單保留截圖 |
| `@API` | 使用內建 `createApi` 或專案的真實 API 工具，以情境指定身分直接呼叫端點 | 記錄經篩選的請求與回應摘要，必要時依同筆 ID 查回業務結果 |
| `@DB` | 專案的查詢工具（如 `sqlcmd`、`psql`），**只下查詢**驗證結果 | 查詢語句與結果摘要寫進報告 |

- 核准的驗證截圖使用 `evidence/<情境編號>_<簡短中文描述>.webp` 或 `.png`，檔名對應情境。其他供代理目視確認的截圖用暫存位置，記錄必要的實際畫面結果後立即刪除，不加入持久 evidence 清單。通過的 UI 情境可用 `REPORT.md#<情境編號>` 記錄操作及觀察到的實際結果作為文字證據。
- **截圖當下就遮蓋個資**：從受測 worktree 對已驗證的 CLI session 執行 `node "<skill 目錄>/scripts/bdd.mjs" cli-screenshot --session <名稱> --filename ".bdd/<本輪>/evidence/<檔名>.png"`，套用 `.bdd/config.json` 的 `mask.selectors`。確認帳號名稱、頭像、Email、電話等均已遮蓋後，以 `node "<skill 目錄>/scripts/bdd.mjs" mask-evidence --dir <輸出資料夾> --mark --pattern <截圖檔名> --method css` 登記。個別頁面缺少適用 selector 時，依[截圖遮罩範例](archive.md#遮罩在截圖當下處理)使用同一 session 的 `run-code` 在截圖當下遮蓋實際欄位。確認整張畫面沒有個資時，用 `playwright-cli -s=<名稱> screenshot --filename="<本輪證據絕對路徑>.png"` 另存新檔，再以 `--method exempt --note <理由>` 登記。
  未遮罩的原圖不要留下，事後補救用 `-Apply` 套座標規則。保留的驗證截圖須有有效遮罩登記；暫存截圖若畫面含個資也必須先遮罩再查看，讀取完成後立即刪除。封存時沒有有效遮罩登記的圖片會被拒絕。
  做法見 [BDD 封存、遮罩與清理](archive.md)〈遮罩〉。
- 前置資料盡量透過 UI 或 API 建立，走真實路徑；只有真的做不到才直接寫資料庫，並在報告註明。
- 序列執行時依 [提前準備測資](parallel-bdd.md#序列執行時提前準備測資) 集中建立互不影響的前置資料，並在各情境使用前核對狀態。
- `@UI` 須逐一執行情境的操作與結果確認，登入前置條件可依上述規則重用。若 `goto` 無法連到 localhost，檢查服務、有效埠、HTTPS 與 CLI 瀏覽器所在主機，確認使用本輪 session 與 `configPath` 後重新探測。仍無法執行時，將受影響的 UI 情境記為「阻塞」，列出錯誤、排查結果與解除條件。
- 每個情境的結果只有四種：**通過**、**失敗**、**阻塞**（環境或前置條件不足而無法判定）、**未執行**。
  失敗要寫「預期 vs 實際」，並盡量指出可疑的程式位置（`檔案:行號`）。
- **「通過」只給走真實路徑驗到的結果。** 如果為了讓畫面跑起來而攔截 API 回應、塞假 token 或假權限，
  那驗到的只是前端在假資料下的行為，後端與權限沒有被驗。這種情境記「阻塞」，
  在備註寫「已以模擬資料確認畫面 X，待真實登入複測」，並在情境加 `@模擬` 標籤，讓讀者一眼分得出來。
- **阻塞時盡量補佐證，但佐證不改判。** 缺登入時，可以跑既有單元測試、或對同一段邏輯做唯讀的資料檢查，
  把結果寫在情境的備註與報告的〈補充佐證〉，說明「邏輯層已確認，只差端對端」。
  情境本身仍是「阻塞」——單元測試通過不代表畫面與授權路徑可用。
- 若發現是**情境本身寫錯**（誤解需求），根據需求修正**模組裡的**情境，並在報告的〈情境修訂〉記下改了什麼、為什麼；不可為了讓結果變綠而降低預期。改完依〈3-1〉送子代理審核被改的情境，審核確認不是降低預期後才重跑。
- `@已知缺陷` 情境照跑。若它竟然通過了，代表當初的判斷錯了，在報告中說明。

### 6-1. 修正、重啟、複測，直到可驗證的 all pass

第一輪先完成真實操作、記錄「預期 vs 實際」及必要斷言；若截圖只為代理判讀失敗畫面，判讀後立即刪除。依核准的清單保留本輪截圖與對應結果。issue 交付取最終驗證輪。依步驟 7 記錄該輪報告及 `verification.json`。接著對每個失敗判斷根因：產品程式缺陷、情境誤解、服務／測試資料問題，或需要使用者提供權限的阻塞。**產品缺陷在本次任務內主動修正，不等使用者再次下令。**

1. 根據需求與實際證據定位最小根因，修正受測範圍內的程式；保留原有需求與驗收標準，不刪除失敗情境、不改成假回應、不繞過登入或權限，也不改動無關功能。已知缺陷修好後移除不再適用的 `@已知缺陷`，記下修正檔案與原因。
2. 執行受影響的單元／整合測試，從**包含本輪修正的工作區**重新建置或重啟獨立受測服務，確認新程式已由本輪測試網址提供，不動使用者原本的服務。在本輪 CLI session 用 `goto` 或 `reload` 重新載入頁面，避免把舊服務或快取畫面當作修正結果。
3. 開發中複測失敗情境與受影響的相關回歸。合併模式在最新 develop 整合後、推送前完整驗證。feature 模式在功能工作區完整執行本次全部情境與必要回歸，通過後才轉換正式分支。明確只要報告的限定任務依指定範圍驗證。分支模式未定時依[收尾模式](closeout.md#7-0-確認收尾模式)處理已授權的 issue 交付與詢問時機。局部通過記「相關情境通過」。每輪更新 `REPORT.md`、`verification.json`，以 `R<輪次>_` 保存新證據與先前的失敗紀錄。新問題回到步驟 1，持續修正與複測。
4. 合併模式的相關情境通過即可準備整合，完整 all pass 是推送閘門。只有失敗、阻塞、未執行皆為 0，且每個情境都走真實路徑驗證，才記「all pass」。已授權回寫的任務接續完成[共用 issue 交付](closeout.md)，再依收尾條件回報。遇到無法取得的帳號／權限、非測試資料庫、無法連線的必要服務，或修正需要超出本次需求範圍的產品決策時，保留已完成的修正與證據，將剩餘情境如實列為阻塞或失敗並說明解除條件。

使用者明確只要情境、不要求執行時，仍依步驟 3 停止，不啟動此循環。
