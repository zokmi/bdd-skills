# 本機執行與複測

**先決定本輪範圍，再執行情境**：依 `SKILL.md`〈先決定驗證階段，再派工〉區分開發回饋與最終完整驗證。合併模式或交付方式未定時，初測也只驗修正與受影響回歸；不是先完整跑一次才開始縮小複測。`rerun`／`no-record` 只使舊結果失效，合併模式的完整重跑安排於候選整合後。開發回饋通過即進整合或詢問交付方式，不以未跑完整驗證為由卡住。必測清單確實等於全部情境時照實跑，不減少必要覆蓋。

每輪實測先完成 `SKILL.md`〈每輪實測的執行模式判定〉；確認版本與本節環境安全後，兩組以上可獨立執行且有子代理名額就依 [子代理並行 BDD](parallel-bdd.md) 自動派工。初測、修正後複測及同步／整合後重跑都適用；情境沒改只是不重做情境審核，不免除實測分組判定。無法並行的範圍序列執行，其他獨立組照常派工。

### 4. 執行前的安全確認

**必須取得使用者對具體資料庫環境的明確確認，才能開始實測。本機與唯讀情境同樣適用。** 順序如下：

1. **盤點實際目標**：讀前端 API 位址、後端生效的連線設定、啟動 profile、環境變數與覆寫來源，列出所有資料庫主機／執行個體、埠（如有）、庫名、租戶（如有）、環境用途、設定來源及本輪讀寫範圍。不輸出密碼、token 或完整連線字串。API 在 localhost、庫名含 Test／Dev 或設定寫 Development 都不能代替確認。未知目標先補齊，不能當作已確認。
2. **展示並詢問**：例如「本次 API 為 http://localhost:5000，實際資料庫為 (localdb)\\MSSQLLocalDB／App_Test，環境 Development，來源為啟動 profile 與連線設定；測試會新增、修改及清理本輪測試資料。請確認這是正確的測試資料庫，並同意在此環境執行本次 BDD。」依實際情境說明唯讀或寫入範圍，多資料庫逐一列出。
3. **等待明確回覆**：收到使用者針對上述目標表示「確認／正確，可以測試」才解除關卡。只告知、已送出問題、選項預選、逾時、沉默或使用者只說「開始測試／直接跑／測到全過」均不算資料庫確認。回覆含糊或否認時先釐清。
4. **確認前不實測**：可讀本機文件／程式／設定、撰寫與審核情境、整理計畫；不可執行 UI／API／DB 情境（含唯讀查詢）、登入、seed、migration、清理資料或啟動可能連庫自動寫入的服務，也不可派實測子代理。子代理缺確認證據時回報主代理等待使用者，不先跑唯讀情境。無法取得確認時列「阻塞：待使用者確認資料庫環境」，不宣稱通過。
5. **記錄與沿用**：報告〈資料庫環境確認〉記錄目標清單、環境、設定來源、讀寫範圍、確認回覆摘要、對話位置／時間（可取得者）及適用輪次。證據須來自使用者；設定檔、舊報告或代理自行宣告不算。同一任務目標與授權範圍未變的複測沿用已取得的明確確認，每輪仍核對設定；主機、執行個體、埠、庫名、租戶、環境或讀寫範圍變更，以及跨 repo 時，停止並重新展示、取得確認。只改 worktree 或版本且目標與範圍未變，不重複問。

環境確認不授權清除未知歸屬資料、全表 DELETE／TRUNCATE 或超出確認範圍的操作。SIT／UAT／PROD 須清楚揭露實際環境與影響，依專案限制執行，不自行改稱開發測試庫。

- 登入帳密向使用者要或從專案文件指定的位置讀，**不要猜、不要寫進 `.feature` 或報告**（報告只寫「以具備 X 權限的測試帳號」）。
- **沒有帳密時，不要繞過驗證**：不自己建帳號、不把帳號加進管理員群組、不用設定檔裡的金鑰自簽 token、
  不改權限資料。這些動作在共用資料庫留下的是一個真的能登入的高權限帳號與稽核紀錄，
  而且測出來的結果也不代表真實使用者的權限路徑。需要登入的情境標「阻塞」，寫明要什麼權限的帳號才能解除。
- **寫入刪不掉的資料要先想清楚**：有些表受觸發器或稽核規則保護，寫進去就刪不掉（例如價格版本、簽核紀錄）。
  驗證這類約束時，把寫入包在交易裡、驗完回捲；需要留下資料才能驗的，先問使用者。

### 5. 準備環境

**啟動服務前的 worktree preflight（每輪測試都先做）**：先從專案文件找出本輪前後端原埠號，
在受測 repo 根目錄執行 `pwsh -NoProfile -File "<skill 目錄>/scripts/loopback-slot.ps1" -Ports <原埠號，逗號分隔>`，
讀取 JSON 的 `isWorktree`、`slot`、`ip`、`chromiumArg`、`occupied`；腳本失敗或無法確認埠號時，
先釐清環境，不要猜 IP 或直接啟動服務。

- `isWorktree=false`：照一般 localhost 流程測試。
- `isWorktree=true`：**先讀 [worktree loopback 操作細節](worktree-loopback.md)**，確認 `occupied` 的程序歸屬後，
  用 `prepare-worktree-mcp.ps1` 產生本輪臨時 MCP 設定，建立可識別的獨立連線並核對前端／API 實際目標與版本；不能只產生設定就視為隔離完成。原始 localhost、埠號與設定檔不可異動。
  讓本輪前後端只綁分配的 `ip`、沿用原埠號；`@UI` 用可配置 `chromiumArg` 的隔離 Playwright MCP session（無法配置時列為阻塞），
  `@API` 用該 `ip`。確認 HTTP 回應屬於本輪版本，再執行情境。
- 占用者若是別的 worktree、使用者服務，或綁 `0.0.0.0`／`::`，不要停掉或借用；
  無法取得安全的本輪服務時，把相關情境列「阻塞」並回報。報告〈環境〉記錄 `isWorktree`、slot、IP、埠號、占用判定與實際 UI／API 網址；
  **缺少 worktree preflight 或無法確認受測服務版本時，不可宣稱該輪 all pass。**

- 依 preflight 的 `ip` 與原埠號檢查服務是否已在跑（監聽資訊、`curl` 健康端點或首頁）；
  worktree 不要把主目錄 `127.0.0.1` 的服務當成本輪服務。
- **確認跑著的就是要測的版本。** 已在跑的後端可能是幾個 commit 前建置的，測它等於測舊程式。
  比對建置產物的時間與 HEAD 最後一次後端異動的時間，或比對 Swagger／路由是否已含本次新增或移除的端點。
  確認不了時，從**包含本輪待測異動的工作區**建置獨立服務，**綁到另一個 loopback IP、沿用原埠號**另起一份
  （見 [worktree loopback 操作細節](worktree-loopback.md)）。若需複製到暫存目錄，也要包含本輪未提交修正；單用 `git archive HEAD` 會漏掉它們。
  不要停掉或重啟使用者原本在跑的服務，也不要改 repo 設定。
- 沒跑就依專案文件啟動；worktree 要明確綁 preflight 的 `ip`，用可用工具在背景執行，等到該 IP 的原埠號可連再繼續。
- 前後端就緒後，實際對本輪前端網址發出 HTTP 請求，確認回應與受測版本；不要只看到程序在跑就認定頁面可用。
  worktree 的服務探測使用 `http://<ip>:<前端埠>/...`，Playwright MCP 頁面網址仍用 `http://localhost:<前端埠>/...` 並帶 `chromiumArg`；
  主目錄照專案原本的 localhost／HTTPS 網址。把確切網址記入報告。

- 啟動失敗、缺帳號、缺資料庫權限 → 相關情境標「阻塞」並寫明原因，其餘能跑的照跑，不要整批放棄。

### 6. 逐情境執行

依情境的標籤選手段：

| 標籤 | 手段 | 證據 |
|------|------|------|
| `@UI` | 必須使用 Playwright MCP：以 `browser_navigate` 開啟受測網址，用 `browser_snapshot` 找元素、`browser_click`／輸入等工具走真實流程，以 `browser_take_screenshot` 保存證據。MCP 不可用、無法連到受測服務或無法滿足 worktree 隔離時，先排查並修復；仍無法執行則列「阻塞」，不得改用 Node Playwright、CLI 或其他瀏覽器工具替代。共用 session 的 UI 情境序列執行 | 關鍵畫面截圖 |
| `@API` | `curl` 帶登入取得的 token 直接呼叫端點 | 請求與回應摘要存 `evidence/<編號>_<描述>.json` 或寫進報告 |
| `@DB` | 專案的查詢工具（如 `sqlcmd`、`psql`），**只下查詢**驗證結果 | 查詢語句與結果摘要寫進報告 |

- 證據檔名：`evidence/<情境編號>_<簡短中文描述>.png`（如 `IC-05_列表單價顯示.png`），一看就知道對應哪個情境。
- **截圖當下就遮蓋個資**：截圖前注入遮罩樣式（帳號名稱、頭像、Email、電話等，選擇器以 `.bdd/config.json` 的 `mask.selectors` 為準），
  確認後以 `mask-evidence.ps1 -Mark -Method css` 登記；畫面本來就沒有個資的用 `-Method exempt -Note <理由>`。
  未遮罩的原圖不要留下，事後補救用 `-Apply` 套座標規則。封存時沒有有效遮罩登記的圖片會被拒絕。
  做法見 [BDD 封存、遮罩與清理](archive.md)〈遮罩〉。
- 前置資料盡量透過 UI 或 API 建立，走真實路徑；只有真的做不到才直接寫資料庫，並在報告註明。
- `@UI` 不可只驗 HTTP 狀態或看首頁就算完成：逐一走情境的登入、輸入、送出與結果確認。Playwright MCP 的 `browser_navigate` 若無法連到 localhost，先查服務、埠號、HTTPS 與 MCP 所在主機；可修復就修復後重試，仍無法讓 MCP 連本機時，相關 UI 情境列「阻塞」，記錄錯誤、排查結果與解除條件，不得改用其他工具宣稱通過。
- 每個情境的結果只有四種：**通過**、**失敗**、**阻塞**（環境或前置條件不足而無法判定）、**未執行**。
  失敗要寫「預期 vs 實際」，並盡量指出可疑的程式位置（`檔案:行號`）。
- **「通過」只給走真實路徑驗到的結果。** 如果為了讓畫面跑起來而攔截 API 回應、塞假 token 或假權限，
  那驗到的只是前端在假資料下的行為，後端與權限沒有被驗。這種情境記「阻塞」，
  在備註寫「已以模擬資料確認畫面 X，待真實登入複測」，並在情境加 `@模擬` 標籤，讓讀者一眼分得出來。
- **阻塞時盡量補佐證，但佐證不改判。** 缺登入時，可以跑既有單元測試、或對同一段邏輯做唯讀的資料檢查，
  把結果寫在情境的備註與報告的〈補充佐證〉，說明「邏輯層已確認，只差端對端」。
  情境本身仍是「阻塞」——單元測試通過不代表畫面與授權路徑可用。
- 若發現是**情境本身寫錯**（誤解需求），根據需求修正**模組裡的**情境，並在報告的〈情境修訂〉記下改了什麼、為什麼；不可為了讓結果變綠而降低預期。改完依〈3-1〉送子代理審核被改的情境，審核確認不是降低預期後才重跑。
- `@已知缺陷` 情境照跑。若它竟然通過了，代表當初的判斷錯了，在報告中說明。

### 6-1. 修正、重啟、複測，直到可驗證的 all pass

第一輪先完成真實操作、保存失敗畫面與「預期 vs 實際」，依步驟 7 的方法記錄該輪報告及 `verification.json`。接著對每個失敗判斷根因：產品程式缺陷、情境誤解、服務／測試資料問題，或需要使用者提供權限的阻塞。**產品缺陷在本次任務內主動修正，不等使用者再次下令。**

1. 根據需求與實際證據定位最小根因，修正受測範圍內的程式；保留原有需求與驗收標準，不刪除失敗情境、不改成假回應、不繞過登入或權限，也不改動無關功能。已知缺陷修好後移除不再適用的 `@已知缺陷`，記下修正檔案與原因。
2. 執行受影響的單元／整合測試，從**包含本輪修正的工作區**重新建置或重啟獨立受測服務，確認新程式已由本輪測試網址提供，不動使用者原本的服務。用本輪的 Playwright MCP 重新導覽／重載頁面，避免把舊服務或快取畫面當作修正結果。
3. 開發中複測失敗情境與受影響的相關回歸；合併模式依 [整合與封存](closeout.md) 將完整驗證集中到最新 develop 整合後、推送前。feature 模式在功能工作區完整執行本次全部情境與必要回歸，通過後才轉換正式分支；明確只要報告的限定任務依指定範圍驗證。開發與相關回歸通過且尚未指定交付方式時，自動依收尾指引詢問兩種方式。局部通過僅記「相關情境通過」，不得宣稱整體 all pass；每輪更新 `REPORT.md`、`verification.json`，以 `R<輪次>_` 保存新證據，不覆蓋舊失敗證據。新問題回到步驟 1，持續修正與複測。
4. 合併模式的相關情境通過即可準備整合，完整 all pass 是推送閘門；其他模式完整通過才收尾。**只有失敗、阻塞、未執行皆為 0，且每個情境都走真實路徑驗證，才寫「all pass」並完成收尾（合併模式才可推送）。** 遇到無法取得的帳號／權限、非測試資料庫、無法連線的必要服務，或修正需要超出本次需求範圍的產品決策時，保留已完成的修正與證據，將剩餘情境如實列為阻塞或失敗，說明解除條件；不要無限重試或宣稱通過。

使用者明確只要情境、不要求執行時，仍依步驟 3 停止，不啟動此循環。
