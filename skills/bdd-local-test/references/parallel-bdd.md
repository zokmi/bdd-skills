# 子代理同時執行多組 BDD

每輪實測由主代理主動評估：可拆成至少兩組安全獨立執行的情境且有可用子代理時，自動進入本流程，不以使用者明說「並行」為前提。子代理各自完成分配範圍內的真實驗證與證據保存，沿用本輪已確認的環境、權限與收尾範圍；並行不擴大資料寫入、issue 更新或整合授權。

將共享瀏覽器、同筆資料與共用服務操作的衝突範圍合成序列組，再判定剩餘組是否可並行；不要因一組衝突讓全部組退回主代理單獨執行。無法派工時於報告記錄具體限制；只做情境審核不算已派實測代理。子代理不遞迴拆組派工，由主代理統一管理名額與依賴。

## 分組與派工

先依 `SKILL.md` 判定驗證階段，再分組：派工附文明列「開發回饋／最終完整驗證」與本輪情境清單。開發回饋只派修正與相關回歸，不因可用多個子代理就擴為完整驗收；合併模式的全部情境派工集中於候選整合後，子代理不自行加開整合前完整測試。

派工、結果與停止確認使用 [結構化輸入輸出契約](parallel-bdd-contract.md)。主代理寫 `assignment.json`，子代理寫各組的 `result.json`；資源停止確認另用 `resource-release.json`，以 runId／groupId／attempt 及停止要求的 requestId 核對，不只依自由文字彙整。

先依功能模組、情境依賴與資源衝突分組，不只按情境數量平均分配。主代理建立派工表，至少記錄：

| 欄位 | 內容 |
|------|------|
| 組別與負責代理 | 唯一組別 ID 與代理名稱 |
| 驗收範圍 | 原始需求、模組 .feature 路徑、情境編號、changed／regression 分類 |
| 受測版本 | repo、工作目錄、HEAD、未提交異動與服務版本 |
| 資源 | UI／API 網址、瀏覽器、帳號角色、測試資料識別與服務管理者 |
| 輸出與修改權 | 每組獨立輸出目錄、允許修改的檔案、前置依賴與禁止共用的資源 |

完整情境清單須覆蓋本輪範圍，每個情境指定一個負責組。必要的重複回歸標明用途；總計按模組路徑＋情境編號去重。依可用代理數量與環境容量分批派工，不假設能無限制同時啟動。沒有子代理工具時主代理序列執行並記錄原因，不宣稱曾並行驗證。

派工內容附上本 skill 與本階段必讀參考、原始需求、已確認環境的依據、分配的情境及上述資源。情境新增或修改仍先 lint，再交另一個未參與該組撰寫或執行的代理依 [情境審核](scenario-review.md) 審核；審核者只讀、不修檔。

## 隔離與共用資源

- **檔案與 Git**：唯讀測試可共享固定版本 checkout；會修改程式的組別使用獨立 worktree，或由主代理指定唯一寫入者序列修改。不得同時修改同一 .feature、MODULE.md、共用設定或操作同一 checkout 的 checkout／reset／merge／commit。情境編號由主代理預先分配，避免撞號。
- **服務**：不同 worktree 各自依 [loopback 隔離](worktree-loopback.md) 執行 preflight，不自行猜 IP。同一固定版本服務可供互不影響的組別共用，但指定唯一管理者；子代理不得自行重啟或停止共用服務。IP 與 worktree 隔離不代表資料庫隔離。
- **瀏覽器**：多組 UI 不共用 Playwright MCP session、分頁、持久化 profile 或可變登入狀態。必須使用 Playwright MCP；只有工具提供明確獨立 session 時才能並行 UI。只能使用共用 MCP 時，UI 序列執行；worktree 的 MCP session 必須能配置其 chromiumArg，無法隔離時列「阻塞」，不得改用其他工具替代。
- **資料與帳號**：每組使用可辨識且互不重疊的測試資料範圍，帳號角色符合情境；同帳號若有單一登入或全域設定也屬衝突。建立／刪除同一賽事、共用 seed、migration、清庫與全域設定不能並行；無法隔離時排依賴序列，其他獨立組可繼續。唯讀組若依賴被修改資料，也須等待資料穩定。清理僅限本組已確認的測試資料，不清除其他組或歸屬未知資料。
- **證據與紀錄**：不同單號沿用各自 `.bdd/<單號>-<主題>/`；同一單號拆組時可用該目錄下 `groups/<組別>/` 保存各組 REPORT.md、verification.json、masking.json 與 evidence/，依 [報告與驗證紀錄](reporting.md) 分別記錄。每個檔案只有一位寫入者，各輪證據保留不覆蓋。使用既有封存腳本時，以各組輸出目錄分別封存，不假設腳本會自動合併或遞迴辨識 groups。

## 失敗、修正與版本變動

子代理回報失敗時附情境編號、預期與實際、證據、疑似根因及受影響檔案。可在獨立 worktree 內修正已分配且不衝突的檔案；共用程式或跨組修正先交主代理協調，由唯一寫入者處理，不讓多組競相修正同一缺陷。

共用服務需重啟或受測程式／資料庫結構／情境變更時，主代理先通知受影響組停止使用該資源、保存當輪證據，收到所有受影響組已停止並釋放資源的確認後，才完成修正、建置與版本確認並派發複測。無回應時先中斷該代理並確認測試程序已停止；僅送出通知或中斷要求不算資源已釋放。不把變動前後的結果拼成同一版本全通過；不受影響的獨立組可繼續。

不同 worktree 的通過僅代表各自版本。整合修正後依 [本機複測](local-execution.md) 與 [整合收尾](closeout.md) 在同一最終版本完整驗證本輪情境及必要回歸；合併模式集中於最新 develop 整合後、推送前，可再按上述隔離規則並行。不得把各分支的局部通過相加當成整合驗證。

## 回報與收尾

每組回傳情境結果清單、四種結果統計、repo／HEAD／工作區及服務版本、實際工具與網址、報告和遮罩證據路徑、修改檔案、阻塞原因及需要的複測。代理中断或沒有回傳的情境記「未執行」，已知缺前置條件的記「阻塞」；其餘可執行組繼續，不用無限重試等待。

主代理逐情境核對派工清單與證據，處理缺漏、重複及版本不一致後產出總報告，連結各組報告與驗證紀錄。同一輪總 verification.json 由主代理依實際受測工作區與情境清單用既有腳本記錄，不拼接不同版本的 JSON；跨 repo／版本維持各自紀錄並在總報告說明，不製造共同 SHA。只有全部情境實測且失敗、阻塞、未執行皆為 0，才宣稱本輪全通過。

整合、推送、issue 更新、封存及服務停止由主代理統一依原收尾流程處理。共用服務等所有使用組釋放後才判定是否停止；子代理不得清理其他組的證據、資料或 worktree。未指定的外部更新不因子代理完成而自動執行。
