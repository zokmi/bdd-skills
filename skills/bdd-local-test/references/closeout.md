# 整合、完整驗證與交付

本章的完整驗證指在最終候選版本跑完依 [品質閘門](quality-gate.md) 確定的本輪範圍。同單追加回饋可在最終候選版本完成本批驗收。依本次改動選入核心、對應情境及必要回歸；整單驗收涵蓋整單有效條件。符合 FULL 條件時執行全套。

### 7-0. 確認收尾模式

實測前先讀本節，依已指定的交付方式決定初測與派工範圍。模式未定時，先完成開發階段的修正與相關回歸、適用的 issue 階段回寫與回覆內容審核，再依下文停止服務並詢問模式。已指定模式時直接沿用。合併模式在候選整合後完整驗證，推送同一 HEAD 並核對遠端。候選整合工作區也可以是 worktree。只有版本或受測條件實際改變才重新完整驗證。

**合併模式**：開發中只複測修正與相關回歸；相關情境通過即可準備整合，不必先取得完整 all pass。完整驗證集中在最新 origin/develop 整合後、推送前，從乾淨 commit 執行本輪選定的全部情境與必要回歸一次。feature 模式在功能工作區完整驗證。明確只要報告的限定任務依指定測試範圍驗證，不進入開發交付流程。

已完成整合完整驗證且程式、情境與環境均未變時沿用該輪。推送同一受測 commit 後只核對遠端 SHA，不再完整重跑。報告與證據不新增到 Git；更新執行產物不改變受測 SHA，也不額外建立文件 commit。

**重測條件**：develop 前進而需重新整合、解衝突或修改改變程式／情境、依賴、設定、資料庫結構或測試環境改變時，重新整合或修正、建置／重啟後再完整驗證。node bdd.mjs verification --check 的 current／still-valid 只涵蓋記錄範圍，不能代替整合驗證。

**自動詢問觸發**：worktree 開發完成、修正與相關回歸情境通過且交付方式未定時，有權回寫指定 issue 的主代理須先完成[本單階段回寫](#本單驗收的階段回寫)與[回覆內容審核](#issue-回覆內容審核)。取得 `PASS` 後依〈服務停止〉停止本輪服務與測試瀏覽器，再主動詢問「轉為正式 feature 分支」或「合併回 develop」。已審核同一階段回覆時核對後沿用。沒有適用的 issue 回寫時記 `N/A` 與原因，依本機條件停止服務再問。僅需開發階段已核准的驗證範圍。

詢問前先提供目前分支、HEAD、相關情境結果及建議的正式 feature 名稱。固定問題：「本次 worktree 開發與相關回歸已完成，要轉為正式 feature 分支，還是合併回 develop？」可用互動詢問工具時提供上述兩個選項；否則以文字詢問。選 feature 時可同時請使用者提供或接受建議名稱。記錄選擇及來源；使用者在本任務已明確指定模式時直接沿用，不重問。尚未回答時保留報告、證據與 worktree，不執行合併、分支轉換、推送或尚未授權的 issue 更新，也不刪除證據或 worktree；逾時、預選項或無回覆都不算選擇。

**限定測試範圍**：使用者明確只要情境或測試報告時，依限定範圍完成，不觸發開發交付詢問。「只保留測試報告」不是第三個成功交付選項；若使用者在詢問後改要求只留報告，記錄為暫停交付、保留成果，不能宣稱 worktree 開發已交付。

| 模式 | 後續流程 |
|------|----------|
| 合併回 develop | 執行〈7-1〉至〈7-3〉，包含整合後推送前完整驗證、遠端核對、issue 更新及本機證據清理。 |
| 轉為正式 feature 分支 | 在功能 worktree 完整 BDD 通過後才執行下列分支轉換；保留工作區、報告與 issue 必要證據供後續開發。 |

**feature 驗證閘門**：選擇 feature 後，先在功能 worktree 最終版本完整執行本輪選定的全部情境與必要回歸；失敗、阻塞、未執行皆為 0 才能建立或更名為正式分支。未通過時保留原分支與證據，修正並重測，不宣稱正式 feature 已交付。已有同一版本、情境與環境的完整驗證可沿用；只有分支名稱改變、HEAD 與未提交內容均未變時不重跑。後續同步 develop、解衝突或受測條件改變時，須在新版本重新完整驗證。此階段只記「feature 功能驗收通過」，不記「develop 整合驗收通過」。worktree 是工作目錄，轉換的是承載成果的分支。

**轉為正式 feature 分支**：本輪已指定名稱時沿用；仍需詢問名稱時，先完成適用的 issue 回寫、回覆內容審核與服務停止判定，再顯示目前分支、HEAD、工作區異動及建議的 `feature/<單號>-<主題>` 名稱。專案有命名規範時依規範建議。用 `git check-ref-format --branch <名稱>` 檢查名稱。若目前已在指定分支，直接沿用；需要轉換時才檢查本機及遠端同名分支，名稱已存在就回報並重新詢問，不覆蓋或強制改名。無法查證遠端時保留現況並回報，不把查詢失敗當成名稱不存在。

- 目前是本輪專用分支時，使用 `git branch -m <名稱>` 改名；若為 detached HEAD 或目前在 `develop`、主分支或共用分支，使用 `git switch -c <名稱>` 從目前 HEAD 建立分支，保留原分支。已在使用者指定的 feature 分支時沿用。
- 轉換後核對分支名稱、HEAD 與工作區異動；HEAD 和未提交內容須保持一致。不將未提交異動自動提交，不刪除舊遠端分支。改名後若仍追蹤舊名稱的 upstream，解除該追蹤，避免後續誤推。
- 遠端推送僅在使用者已要求時，以非強制方式推送並設定同名 upstream；否則記「僅本機轉換」。推送失敗保留本機分支並記錄原因。
- 將原分支、正式名稱、受測 SHA、推送狀態與 worktree 保留原因寫入〈收尾紀錄〉。此模式不執行〈7-1〉的 develop 合併或 issue 結案，不自動清理 worktree。最終完整驗證全通過後，依〈共用 issue 交付〉追加修正說明與必要驗證證據，完成回覆內容審核後依〈服務停止〉處理。依〈7-3〉清理已核對的必要截圖，保留工作區與報告。

以下〈7-1〉的合併流程及 worktree 清理規則只適用於使用者選擇「合併回 develop」。各模式依〈服務停止〉的共用條件判定。

### 本單驗收的階段回寫

依 [Issue 優先驗證與回寫](execution-workflow.md#issue-優先驗證與回寫)，已授權更新唯一指定 issue 且本輪直接驗收項目已通過時，若另有相關測案待驗，或開發完成後仍待使用者選擇分支模式，先做階段回寫。主代理提供本階段已驗清單、同版證據與待驗項目，依〈共用 issue 交付〉取得寫入前的獨立結果報告審核與一致性審核 `PASS`。階段註記只陳述實際驗過的範圍；待選模式時標明最終候選版本尚待驗證。已指定模式且無其他相關測案待驗時直接依最終交付條件辦理。

主代理派一名具 issue 工具權限的專責子代理，提供唯一單號、本批回饋或整單驗收範圍、對應原條號與註記位置、受測版本、核准項目的實測結果與證據、該範圍內待驗項及允許追加的欄位。寫 Redmine 前先讀 `~/.redmine-issue-guides/SKILL.md`、專案規範和適用的 `redmine-issue-writing` 指引。依 issue-writing skill 的驗證完成模板及下節〈逐條回覆驗收標準〉追加結果，說明待驗回歸或最終候選狀態。保留原需求、驗收條件及 issue 狀態。

子代理寫入前讀現有紀錄，已存在相同回饋批次與範圍、同階段及受測版本，且結果相符的註記時直接核對；寫入後回讀並回報註記識別與核對結果。短暫失敗時先重讀，只補缺項。主代理依下節取得該註記的審核 `PASS`，再放行其餘測案。仍無法審核、派工、寫入或回讀時，保留草稿與證據，回報具體阻礙及待驗清單。

### 逐條回覆驗收標準

已授權的 BDD 階段與最終回寫都依本節核對內容。派工時明列核准範圍、該版本各條的觀察結果與證據，並提供使用者對回覆方式的明確要求。

1. 本批回覆交代回饋來源、受測版本及本批結論，涵蓋本批核准的條目，對應原單時保留原條號，新增回饋用註記及可辨識的條文定位。整單回覆才依完整驗收標準及後續修訂逐條核對；沒有獨立章節時，以明列的需求對照。每項寫出判定及本版實際觀察到的結果。同一條包含多個操作、選項或結果時，逐個交代。區分直接驗收與額外回歸的結果。
2. 逐條核對同版實測斷言。部分驗證、失敗、阻塞或未驗的條件要點名，寫出已有結果、缺口與原因。列出仍待需求方確認的行為。本批各條及其子條件均有同版通過證據時可寫「本批回饋驗證通過」。使用「整單驗收通過」須有該版本逐一驗證整單全部有效條件並通過的證據。引用歷史註記時標出其原批次及受測版本，該結果只在原輪次計數。報表的情境 PASS 數或程式差異不能填補缺項；應補驗時先補驗，再觸發全過回寫。
3. 每個已驗的畫面結果都要有該階段受測版本、經目視審核及遮罩的截圖，並寫明圖中可見的值或狀態。同一張圖佐證多條時，逐條說明可見依據。需比對修正前後時，核對修正前的原圖，缺圖時說明證據缺口。外觀相同但前置狀態不同的圖片，要在首次回覆中說明差異與佐證來源。
   - Excel 欄名、欄序或下拉選項等可見結果，開啟本次匯出的檔案，擷取對應畫面。整檔筆數或匯入後資料一致性另列實際比對結果。
   - 純 API、DB 或沒有可視結果的檔案檢查，說明截圖不適用的原因，列出可核對的實際回應、查詢值或檔案內容。條件兼含畫面與資料時，分別交代畫面觀察與資料實測值。
4. 附件上傳、內嵌語法與註記版面依 issue-writing skill 的驗證完成模板。

### Issue 回覆內容審核

每次階段或最終回寫並回讀後，主代理立即指派未撰寫或執行該次回寫的唯讀子代理，依 [bdd-issue-reply-audit](../../bdd-issue-reply-audit/SKILL.md) 獨立審核。提供單號、回饋來源、註記及附件識別、該階段核准範圍、實際異動與同版驗證結果。審核者依本批或整單條目及其子條件反查線上回覆及相應的同版證據，並確認回覆所宣稱的範圍相符。

主代理在報告保存審核結論及其對應的註記、附件與受測版本。只有獨立審核 `PASS` 才放行。收到 `FAIL` 時依該 skill 處理缺漏，更正後回讀並送獨立複審。回寫、回讀或派審遇阻，或審核回報 `BLOCKED` 時，保留服務、瀏覽器與必要證據，回報阻礙，暫緩分支詢問。

接續同一階段時，主代理核對單號、已驗範圍與版本、線上註記內容及附件均與該次 `PASS` 記錄一致，即可沿用。新增或更正回覆、替換附件或改為最終交付，均須審核該次實際交付內容。只要報告、無對應 issue 或使用者未授權回寫時，註明回寫與回覆內容審核 `N/A` 及原因；已授權且應辦的回寫或審核遇阻時仍列待完成。

### 共用 issue 交付：最終完整驗證後自動執行

**觸發與範圍**：指定 issue 已獲回寫授權，本輪核准的條件與子條件在最終受測版本逐一驗證通過，且依〈7-0〉完成本輪全部情境與必要回歸，通過數大於 0，失敗、阻塞、未執行、skipped、pending 均為 0 時，主代理自動接續交付。feature 模式在功能驗收後執行；合併模式依〈7-1〉完成整合驗證、推送與遠端核對後執行。局部回歸通過、不同版本結果拼接或舊輪次證據均不能觸發。這是當次任務的連續執行步驟，沒有背景監控器。

使用者明確只要情境／報告、禁止更新 issue 或本輪未授權回寫時，在報告記錄回寫不適用及原因。沒有唯一 issue 時先查原始需求與專案設定，仍無法確認就回報缺少目標。本規則僅涵蓋追加修正註記及驗證附件，保留原需求、驗收標準與既有紀錄；未另有明確授權時保留狀態、不自動關單，也不擴張 Git 推送或 worktree 清理權限。

主代理負責步驟 1 的審核與交付協調，審核通過後由專責子代理執行步驟 2 至 3 的寫入、附件上傳與回讀，再由主代理核對回傳結果並送[回覆內容審核](#issue-回覆內容審核)。合併模式的〈7-1〉步驟 3 同樣適用。最終註記標明交付範圍是本批或整單，呈現該候選版本的逐條結果。重用已上傳的附件須能追溯到本輪使用的同版證據。

1. **結果報告審核**：先將已核准的驗證清單、最終 `REPORT.md`、`verification.json`、受測版本與對應證據交未參與實測或報告撰寫的唯讀子代理。逐項核對清單與實際操作、預期／實際結果、統計及版本一致性，目視確認核准的 UI 截圖可讀、對應情境且已遮罩登記，並核對 API／DB 替代證據。記錄審核者、受測版本、缺漏與 `PASS`／`FAIL`／`BLOCKED` 於〈結果報告審核〉。缺漏先補正並複審，需重測時沿用實測前審核流程。結果報告取得 `PASS` 後才進入 issue 回寫。主代理重讀目前 issue、repo／commit、工作區狀態、情境、環境與最後一輪結果及必要交付證據；版本或受測條件變更時依〈7-0〉重測。依〈7-1〉步驟 3 動態選唯讀一致性審核 skill 並派子代理，只有 `PASS` 才可寫入；其他結果停止回寫並列出原因。寫 Redmine 前先讀 `~/.redmine-issue-guides/SKILL.md` 與專案規範。
2. **依 issue-writing skill 交付**：先讀當下適用的 issue-writing skill 與其驗證完成模板。依[逐條回覆驗收標準](#逐條回覆驗收標準)填入該模板，沿用其標題、區塊、欄位、順序、用語與寫入落點。將使用的 skill、模板來源及版本（可取得時）記入本機報告；找不到適用 skill 或無法讀取模板時，先查找，仍不可取得則保留草稿與證據並回報阻礙。沿用〈7-1〉步驟 3 的遮罩與防重複流程。測試時間、環境、版本、統計與技術細節保存在本機報告，依模板要求帶入 issue。
3. **回讀與回報**：重新讀取已刊登的註記，逐條核對實測結果與證據，按模板確認已刊登的附件與引用，記錄註記識別、附件連結及核對結果。重試前先讀現有紀錄，只補缺項，避免重複留言／附件。工具、權限、上傳或回讀失敗時保留 issue 交付必需的原始證據與可貼上的草稿；代理驗證用的暫存截圖仍依規則即時刪除。分別回報 BDD、註記、附件、回讀狀態及阻礙；feature 模式仍保留 worktree。

### 7-1. 整合 develop、完整驗證後推送並更新 issue

步驟 2 依 [Issue 優先驗證與回寫](execution-workflow.md#issue-優先驗證與回寫) 執行本單驗收、授權的階段回寫及其他相關測案。步驟 3 依遠端核對後的正式交付條件辦理。

使用者已選擇「合併回 develop」後，依序完成本節，不逐步重問。最終註記使用整合驗證的必要截圖；階段註記使用該階段受測版本的圖。代理驗證用的其他截圖在判讀並記錄文字結果後立即刪除，不因待收尾而保留。每一步把成功狀態寫入〈收尾紀錄〉；任何一步失敗就停止後續合併或更新，不宣稱「已結案」，把已完成的部分、錯誤與下一步回報使用者。若使用者明確只要測試報告、不要更新 issue 或合併，遵照該次要求。

1. **確認目標與準備提交**：由使用者指定的單號、分支或專案設定找出唯一 issue 與其系統（如 Redmine），確認目前是對應的功能分支、遠端 `develop` 存在、最新一輪修正與相關回歸情境已通過；完整 all pass 於整合後取得。若單號、issue、目標 repo 或 `develop` 不明，先查專案文件與遠端；仍無法唯一確認就停止收尾並回報。檢查原有未提交異動，只挑本次修正、模組情境及共用設定提交（見 [版控分工](version-control.md)）；本輪報告、驗證與遮罩紀錄及證據不提交，不夾帶其他人的變更；無法分離時停止合併並說明。提交修正與情境後確認工作區乾淨，直接進入整合，不因提交再完整重跑。保留開發輪次報告；正式受測 SHA 與完整結果於下一步記錄。
2. **合併與驗證 develop**：先把功能分支的 `.bdd/` 報告、`verification.json` 和核准的驗證證據保存在可讀的暫存位置；不搬移已判讀並刪除的代理暫存截圖。若這些檔案未進版控，整合工作區不會自動帶入。`git fetch origin develop`，從最新 `origin/develop` 建立隔離的整合工作區；用 `git log origin/develop..<功能分支>` 與 diff 確認待合併範圍沒有無關變更，再將修正與相關回歸已通過的功能分支合併進去。把前輪報告、核准的驗證證據及必要交付材料帶到整合工作區；新一輪必要截圖使用新的 `R<輪次>_`。
   **衝突全部落在 `.bdd/modules/` 底下時自行解**，做法見 [模組情境集](modules.md)〈並行分支撞號〉；合併後一律跑 `node bdd.mjs modules --lint`，有問題先改號再重跑。
   遇衝突就保留原分支與整合工作區供檢查，停止並回報衝突檔案；不動 `origin/develop`，不推未解衝突版本。合併後建置／重啟整合工作區服務，確認測試網址提供此版本，再依〈1-1〉記錄差異，在乾淨 commit **完整執行本輪選定的全部情境與必要回歸一次**；尚未完成整合驗證時不可因 current／still-valid 跳過。確認 API、UI、資料庫與既有整合沒有退步；若有失敗或阻塞，不推 `develop`，回報原因與證據。全部通過才用非強制的 `git push origin HEAD:refs/heads/develop` 推送整合工作區的 HEAD，再查遠端 SHA 核對；遠端前進、權限不足或分支保護拒絕時，不用 `--force`，回報本機結果與待處理步驟。若原本就在 `develop`，先 fetch 並確認已包含最新 origin/develop；同一乾淨 commit 與環境已有完整驗證時沿用，否則完整驗證後才推送。推送後只核對遠端 SHA。遠端前進而需重新整合時，重新整合並完整驗證。這輪受測程式 SHA 與最後的遠端 HEAD 都要記錄。
3. **一致性審核閘門**：更新 issue 前，依當下 issue 系統與單號、本批或整單的需求來源、repo／分支／commit 範圍、BDD 報告與可用 skill 清單，動態選擇最合適的唯讀一致性審核 skill。Redmine issue 且需要需求／程式雙向比對時優先選 `issue-code-consistency-check`；找不到適用 skill 時結果為 `UNAVAILABLE`，不得繞過審核。派子代理只讀原始需求、git 事實與證據，不修改程式、測試、BDD 輸出或 issue；只有 `PASS` 可進入下一步，`FAIL`、`UNVERIFIED`、`UNAVAILABLE` 都停止 issue 寫入並回報原因。
   〈結果報告審核〉與一致性審核皆取得 `PASS` 後，依〈共用 issue 交付〉的模板追加給 PM 的結果。依[逐條回覆驗收標準](#逐條回覆驗收標準)核對驗收結果與必要證據，按模板交付。保留原概述與驗收標準，狀態更新依已授權的專案流程執行。
   上傳前檢查必要截圖不含帳密或不應外傳的資料，並以 `node "<skill 目錄>/scripts/bdd.mjs" mask-evidence --dir <輸出資料夾> --status` 確認要上傳的圖片全部是 `masked`；有 `unmasked`／`stale` 就先遮罩、登記再上傳。確認 issue 註記與每張必要截圖附件真的儲存成功，記下 issue 連結及附件清單。若註記已儲存但附件失敗，分別記錄「註記已更新／附件未完成」，重試前先讀現有註記，避免重複留言。沒有可用工具、附件上傳失敗或權限不足時，保留核准的驗證截圖、重試交付所需證據與可貼上的說明，回報使用者；不要假稱已更新或只貼尚未上傳的圖片連結。
4. **準備完成紀錄**：在報告〈收尾紀錄〉先列出合併前後 SHA、`develop` 遠端核對、整合後推送前完整驗證結果、issue 連結、必要修正截圖與上傳狀態。將線上回覆送[回覆內容審核](#issue-回覆內容審核)，取得 `PASS` 後依下節處理服務，依〈7-2〉完成最終報告，再依〈7-3〉清理必要本機截圖與 worktree。各項如實記錄完成狀態與阻礙。

### 服務停止

**停止服務的共用條件**：最新一輪指定範圍 BDD 全部通過（通過數大於 0，失敗、阻塞、未執行皆為 0），本機結果與必要證據已保存、截圖驗證審核已通過（或已記錄不適用），該階段應辦的 issue 回寫與回讀已完成、獨立回覆內容審核取得 `PASS`（回寫不適用時記 `N/A` 與原因），且所有使用該資源的實測代理已釋放。開發回饋的局部通過不代表最終完整驗證；仍需立即接續測試或重啟時，記錄保留原因。

主代理在 `REPORT.md` 記錄本輪截圖驗證審核結果。逐張目視判讀本輪用於驗證或交付的截圖，核對畫面可讀、對應受測版本與情境、清楚呈現預期結果；必要交付截圖另確認遮罩及登記。代理暫存截圖可採用代理刪除前記錄的目視判讀結果。全部符合才記 `PASS`；應有截圖缺漏、待審或不合格時保留服務與測試瀏覽器，補拍或修正後複審。未使用且無需截圖的輪次記 `N/A` 與理由。重拍或受測版本變更時，須以最新一輪證據重新審核。

條件全部成立且已無待驗項目使用該資源時，主代理立即自動停止本輪 worktree 啟動的服務與登入／測試用 Chromium，保留工作區、瀏覽器 profile、非圖片報告及必要 issue 證據。需要詢問收尾模式時，依〈7-0〉在停止判定與程序核對完成後詢問；應停止而未成功時保留程序資訊並回報。

**執行觸發點**：每輪保存驗證結果後先審核截圖。適用 issue 回寫時，待回覆內容審核通過，再判定上述停止條件。限定報告或不適用回寫時，記錄原因後即依本機條件處理。最終回覆前再核對埠與瀏覽器程序；無法取得主機程序資訊時回報阻塞，不把空白沙箱程序清單當作已停止。

一般 checkout 與隔離 worktree 都從啟動瀏覽器的工作目錄執行 `playwright-cli -s=<本輪 session 名稱> close`，逐一關閉本輪具名瀏覽器。確認各 session 已關閉後，再清理各組的 CLI 暫存目錄。

核准的驗證截圖保存在本輪 `evidence/`；需交付 issue 的截圖另依附件核對流程清理。其他供代理即時驗證的截圖另存暫存位置，讀取後立即刪除，不進入 `evidence/` 或封存。既有 `evidence.zip` 依[舊封存清理](archive.md)處理。

**達成上述條件且在 worktree 裡測時，逐一停止本輪功能與整合 worktree 綁在各自 `127.0.0.N` 上的前後端服務**，
釋放埠號與記憶體（不必問使用者）。有任何失敗、阻塞或未執行就不停，保留給下一輪複測；一般主目錄（`isWorktree=false` 且未指定 `--isolate`）一律不停。明確以 `--isolate` 啟動的多專案主 checkout 屬於本輪隔離服務，清理時對同一工作區使用 `node bdd.mjs stop-slot-services --isolate`，仍須核對路徑歸屬，不能套用到使用者一般 localhost 服務。

1. 先核對背景工作確實屬於本輪 worktree 啟動的服務，再用可用的背景工作停止工具結束（例如 `run_in_background`／`TaskStop`）；不停止其他工作區或無法確認歸屬的背景工作。
2. 在每個本輪 worktree 的目錄內分別跑停止腳本，帶上該輪保存的 `effectivePorts`，收掉本輪殘留的子程序：
   ```bash
   node "<skill 目錄>/scripts/bdd.mjs" stop-slot-services --ports "<本輪有效埠，逗號分隔>"
   ```
   腳本只停「監聽在本 worktree 專屬 IP 上、且執行檔或命令列位於本 worktree 路徑下」的程序（連同 `dotnet run`／`npx` 等啟動器）；
   主目錄的 `127.0.0.1`、綁 `0.0.0.0`／`::` 的程序、路徑不在本 worktree 的程序都只列在 `skipped`，不會動。
   不確定時先加 `--dry-run` 看會停哪些。
3. 檢查退出碼與 JSON。若 `remaining` 有仍在監聽的埠、`remainingPids` 有仍在執行的目標、`terminationErrors` 記錄停止錯誤，或 `skipped` 有預期應停止的服務，回報具體原因並保留程序資訊。
4. 腳本也選取 `--user-data-dir` 解析後位於本 worktree 下的 Chrome／Chromium／Edge 主程序，連同子程序結束；不需它監聽服務埠。個人 profile、其他 worktree、只有頁面網址包含本 worktree 路徑者一律保留。以 `browsers` 核對選取清單，`--dry-run` 不執行停止。另核對本輪瀏覽器已退出，不能只看 `remaining` 的服務埠。
5. 在 `REPORT.md` 標題表格填「服務狀態」列，包含瀏覽器停止結果與保留原因。

### 7-2. 完成最終報告

先將實測結果與對應證據填進 `REPORT.md` 供審核。完成回覆內容審核與服務停止判定後，再將實際審核及停止結果補進〈收尾紀錄〉，連同最後一輪 `verification.json` 核對。報告記錄受測程式 SHA、情境版本及已核對的遠端 HEAD；不建立或推送純報告 commit。報告記錄 Redmine 連結、附件 ID、受測 SHA 及情境。未驗證的附件列為待處理。已有 Git 追蹤的輸出依 [版控分工](version-control.md) 遷移，不自動提交更新或丟棄異動。限定報告任務保存本機檔案，不自行推送 develop 或更新 issue。

### 7-3. 保留報告並清理本機截圖

1. 確認本次交付的回覆內容審核已 `PASS` 且證據仍對應線上註記及必要附件。記錄附件 ID 或網址、受測 SHA、情境及必要本機遮罩截圖的 SHA-256。純 API／DB 項目記錄已交付的替代證據。
2. 將報告中的本機圖片連結換成已核對的 Redmine 附件連結。保留 `REPORT.md`、`verification.json`、`masking.json` 和本輪受測情境。合併模式在移除 worktree 前，先把這些非圖片檔保存到 worktree 外的本機報告目錄，核對副本可讀且 SHA-256 一致，再記錄保存位置。
3. 代理驗證用的暫存截圖在判讀後立即刪除。issue 必要截圖只逐檔清理已核對附件的本機副本：先確認解析後的路徑仍位於本輪 `evidence/`、未穿越符號連結或 junction，且檔案 SHA-256 與核對紀錄一致。附件缺少、不可讀或本機檔案已變動時，保留該必要圖片與所在 worktree，以便完成交付。交付依驗證完成模板處理必要附件，收尾不建立或上傳圖片 ZIP。
4. 合併模式確認遠端 SHA、非圖片報告副本及服務停止結果後，用 `git worktree list --porcelain` 逐一核對本輪功能及整合 worktree。記錄要移除的絕對路徑，以 `git status --porcelain=v1 --untracked-files=all --ignored` 逐一檢查未提交、未追蹤與忽略檔案。一般 `git worktree remove` 也會刪除忽略檔案，先確認需要保留的資料已移出並核對副本，記錄確認可隨本輪工作區移除的剩餘檔案。feature 與報告模式保留 worktree。
5. 從工作區外對每個目標執行 `git worktree remove <絕對路徑>`。保留結束碼及錯誤，重新讀取 Git 清單，並檢查原路徑在磁碟上是否仍存在。Git 清單已無該筆且原路徑已消失，才記為已移除。
6. 若 Git 仍有登記或磁碟仍有殘留，先釋放可確認屬於本輪的程序或終端機所占用的檔案與目錄。仍有 Git 登記時，排除原因後重做檔案檢查並重試一般移除。若 Git 已解除登記但磁碟仍有殘留，重新核對原絕對路徑及殘留項目，確認路徑未穿越符號連結或 junction，且每個殘留檔案皆屬於移除前確認可刪的項目。逐項移除後由內往外移除空目錄，再核對 Git 清單與磁碟。保留無法確認或仍被占用的項目，記錄具體路徑及阻礙。不可用 `--force`、全域 `git worktree prune` 或遞迴刪除整個 worktree 取代上述步驟。

最後列出本次建立的 `BDD-` 測試資料，**問使用者要不要清除**，不要自己刪。
回覆依模式提供實際結果，未執行的流程不列成待完成：

- **共同欄位**：收尾模式（未選擇時寫待選擇）、受測版本、通過／失敗／阻塞／未執行數字、報告位置、截圖驗證審核、issue 回覆內容審核（或 `N/A` 理由）、服務停止結果與 worktree 保存狀態。
- **合併模式**：補功能分支與 develop 受測 SHA、合併與遠端核對、issue 及證據連結、本機非圖片報告位置，以及證據和 worktree 清理結果。
- **feature 模式**：補原分支 → 正式分支、HEAD 與未提交內容核對、upstream／推送狀態、worktree 保留位置；依〈共用 issue 交付〉附 issue 連結、逐項修正與驗證附件、回讀結果，未完成列阻礙，明確限定不回寫時列不適用原因。附實際清理結果。
- **報告模式**：列出本機報告與核准驗證截圖的保存位置，以及仍待核對的 issue 必要截圖。

任何已選流程的步驟失敗，列出卡住的步驟、錯誤與下一步；同步後複測另說明與上一輪的差異。
