# 分階段工作流程

### 先決定驗證階段，再派工

進入本機實測前就讀 [整合與封存](closeout.md)〈7-0〉，確認本任務已指定的交付方式，不等到收尾才讀。每次派工明列「開發回饋／最終完整驗證」及情境清單：

依 [品質閘門](quality-gate.md) 決定每輪範圍。最終完整驗證指在最終候選版本跑完該輪選定範圍。先區分「本次回饋批次」與「整單驗收」，再依風險決定 TARGETED 或 FULL。同單多批預設使用本次回饋，最終候選版本也只執行該輪核准的清單。

| 目前狀態 | 本輪驗證範圍與下一步 |
|----------|----------------------|
| 合併回 develop，尚未整合 | 只驗修正與受影響回歸，通過後提交並進入整合；不為取得 all pass 預先全跑。 |
| 交付方式未定 | 已授權更新 issue 時，先完成本單已驗範圍的階段回寫與 Issue 回覆內容審核。審核 PASS 後接續所需回歸，通過後依停止條件處理服務，再詢問交付方式。回寫不適用時記 N/A 與原因。回答前只做開發回饋範圍的驗證。 |
| 已選 feature 或明確只要實測報告 | 在功能工作區完成指定範圍的完整驗證。 |
| develop 候選整合已完成 | 在乾淨候選 commit 完整驗證一次，通過後推送同一 HEAD；推送後只核對遠端 SHA。 |

`rerun`／`no-record`、子代理自動分組與「測到全部通過」都不改變上述時機。開發回饋所需情境若恰好等於全部情境，照實執行並記範圍；不能省掉必要回歸，也不能把它當作尚未完成的整合驗收。若使用者明確要求整合前完整測試，依要求執行並說明整合後仍須驗證新版本。

### 實測範圍審核

依[送審前準備](scenario-review.md#送審前選取範圍與編製清單)選取範圍並編製逐項斷言清單。符合小型 TARGETED 條件時，由一名唯讀規劃者一次完成；其餘實測輪次依序派兩次準備。送審時固定候選版本、實際 diff、驗證階段、清單與略過理由。開始 UI／API／DB 實測或派實測子代理前，由未參與本輪規劃或執行的子代理唯讀審核。提供 issue 原文與驗收條件的來源（無 issue 時提供原始需求）、基準與候選版本、未提交差異、實際選取的情境編號與路徑、相關 Feature、略過理由及逐項手段與證據。新增或變更情境時，同一次派工可一併完成情境審核與實測範圍審核，分別記錄結論。

審核者逐條將本輪應驗的要求對到所選情境的實際斷言或工程驗證項目。依 [情境等級與必測範圍](scenario-priority.md) 和 diff 核對適用變更類型、受影響的 P0、核心路徑、必要回歸及略過理由。開發中只複測部分需求時，列明延後驗證的條件與安排；本批最終驗證覆蓋該批全部條件及受影響回歸；整單驗收逐條核對原單與後續修訂。每個擴大的項目要有回饋、diff、依賴或品質閘門依據。回報 PASS 或 FAIL，附上需求與驗證項目對照、缺漏或選入無關情境的依據。無法取得需求或 diff 時回報 BLOCKED。

對外業務行為需求對應所選情境及斷言；工程調整依 [情境範圍](feature-guide.md#情境範圍) 對應技術檢查及證據，不要求情境編號。本輪核准範圍內的每個驗收條件都須有驗證安排。

漏選既有情境時補入清單。對外業務行為缺少可驗證的斷言時，新增或修改情境並完成 [情境審核](scenario-review.md)；工程驗證缺漏則補檢查項目與證據計畫。主代理處理缺漏後，送更新清單複審，取得 PASS 才開始實測。需求、候選版本、diff、情境或清單變更時，先更新受影響的選測與驗證項目，再重新審核。條件與先前 PASS 完全相同的重試可引用該紀錄。無法派出獨立子代理時，保留測試計畫並回報審核阻塞。把候選版本、選測清單、審核者、對照與結論寫入報告〈實測範圍審核〉。

### Issue 優先驗證與回寫

有指定 issue 時，在同一份實測清單標出直接驗證本批回饋的項目及其他受影響回歸。直接驗證包含與本批驗收條件對應的既有情境、技術檢查及必要前置。整單模式則以整單各條與後續修訂選取必驗項。以斷言與需求的對應判定，情境標籤可協助查找。選測與獨立審核仍涵蓋本輪依品質閘門指定的全部範圍。

每輪都依需求、實際 diff 與測案斷言標出直接驗證主要異動的情境或技術檢查，例如重現原缺陷並確認修正、驗證新增或修改的關鍵規則，以及直接受改動的權限或資料保護。把這些項目及其必要前置列為第一批，連同排序依據送實測範圍審核。以實際受影響的行為決定順序，`@core` 與 `@P0` 仍用於標示模組主流程與業務風險。沒有指定 issue 時也先完成第一批，再派工執行其餘核准測案。第一批無適用項目時，記錄原因並從其餘核准項目開始。

1. 先由實測子代理完成核心異動及必要前置，再驗證本輪清單內其餘條目與子條件，逐項核對同版實測證據。缺測先補驗，失敗依既有修正、重啟與複測流程處理，有阻塞時記錄實際範圍。本批或整單核准的直接驗收條件逐條通過且已授權回寫時，若交付方式未定或仍有單外相關測案待驗，依[階段回寫](closeout.md#本單驗收的階段回寫)取得結果報告及一致性審核 PASS，交專責子代理更新 issue 並回讀。已指定交付方式且沒有其他相關測案時，依該模式的最終交付條件回寫，省略階段註記。
2. 每次回寫後，主代理依 [Issue 回覆內容審核](closeout.md#issue-回覆內容審核)派未參與該回覆撰寫或寫入的唯讀子代理，從 issue 讀取實際儲存的註記與附件，逐項比對調整說明、核准的已驗範圍及同版證據。審核 PASS 才可放行其他相關測案。若有缺漏或不符，由專責子代理依已授權範圍更正、回讀並重送獨立審核。遇到暫時失敗先查現有紀錄，只補缺項。仍無法完成時保留服務與證據，回報具體阻礙及待驗清單。
3. 使用者明確只要情境／報告、禁止更新 issue，或本輪未授權回寫時，將回寫及 Issue 回覆內容審核記為 N/A 並說明原因。本批直接驗收項目完成後依原核准範圍驗證其他相關測案。

主代理按階段記錄受測版本、結果、回寫者、註記識別、回讀狀態、Issue 回覆內容審核的審核者與結論及待驗項目。回歸失敗後若修正造成受測版本或條件變更，依範圍審核與版本比對規則先複測已受影響的本單項目，回寫時以實際受測版本為準。完整驗證、推送及最終交付仍依既有條件執行。

### 每輪實測的執行模式判定

初測、缺陷修正後複測、`rerun`、feature 完整驗證與整合後驗證，都在既有執行時機先判定一次；只產情境或整理既有報告而不實測時不派實測代理。此判定不額外增加測試輪次。

1. 主代理確認本輪情境、受測版本與環境安全，依上節順序在各階段按模組、依賴、資料與瀏覽器衝突分組，不以情境數硬切；一組也必須分配給實測子代理，不得把有順序依賴的單一情境拆開湊組。
2. 每輪有實際測試時都必須由子代理執行。先讀 [子代理並行 BDD](parallel-bdd.md)，為每組建立派工契約並實際派工；可用名額少於組數時分批逐組派工，同一代理名額可在前一批完成後再次使用。使用者只說「測到全過」「複測」或「只給報告」也適用，不另問是否要用子代理。
3. 部分組衝突時採混合模式：衝突組由子代理序列執行，獨立組由子代理分批或並行執行。不可因只有一組、情境相依、暫時沒有空閒名額而改由主代理執行；等待名額並分批派工。平台沒有子代理派工能力，或使用者明確禁用子代理時，停止實測並回報阻塞及原因。不得為啟用並行改用假資料／繞過環境確認。
4. 執行前簡述所選模式及分組依據，寫入報告〈BDD 執行模式〉；派工後記錄實際代理與契約位置。子代理本身不遞迴派實測代理，只執行主代理分配範圍；需要再拆組時回報主代理。

情境獨立審核仍依原流程執行，不由執行該組的代理自行審核。無法派工時回報具體限制並停止實測，不假稱已派工或改由主代理執行。

範圍審核 PASS 且環境確認完成後，依[並行準備服務與測資](parallel-bdd.md#並行準備服務與測資)派當前批次的準備任務，並將就緒資訊交給負責該情境的實測代理。即使情境共用資源而須序列執行，服務與測資仍可依相依條件並行準備。序列情境依[提前準備測資](parallel-bdd.md#序列執行時提前準備測資)維持原驗證順序。

1. **確定範圍、版本與情境**：讀 [範圍、版本比對與情境撰寫](workflow-and-scenarios.md)。寫 `.feature` 前讀 [情境寫法](feature-guide.md)；使用模組時讀 [模組情境集](modules.md)。情境寫完後讀 [情境審核](scenario-review.md)。使用者只要情境時，在審核與未執行報告完成後停止。
2. **本機實測與修正**：需要執行時讀 [本機執行與複測](local-execution.md) 及 [報告與驗證紀錄](reporting.md)；worktree 另讀 [loopback 隔離](worktree-loopback.md)。逐情境保留證據，每輪先記錄結果與版本；失敗後修正、重啟並重測。
3. **報告**：需要報告時讀 [報告與驗證紀錄](reporting.md) 和 [報告範本](../assets/REPORT-template.md)。最終實測後依 [結果報告審核](closeout.md#共用-issue-交付最終完整驗證後自動執行) 的核對規則核對清單、報告與證據。使用者只要測試報告時不整合或更新 issue；若需封存，再讀下階段的封存步驟。
4. **整合與收尾**：已授權回寫時，該階段 Issue 回覆內容審核 PASS 後才依[服務停止條件](closeout.md#服務停止)處理服務與測試瀏覽器。回寫不適用者沿用本機停止條件。交付方式未定的開發任務在所需回歸與服務處理完成後詢問分支選擇，已指定模式者直接依該模式收尾。回覆前核對程序與埠。遮罩、封存或清理時讀 [封存指引](archive.md)。

建立 `.bdd` 輸出前，依範圍指引呼叫內部 CLI 的 `gitignore` 子命令，自動驗證並補齊目標 repo 的忽略規則；切換 repo/worktree 或整合後重新檢查。衝突及已追蹤產物依 [版控分工](version-control.md) 處理。

各階段只讀當前需要的參考文件，不把整套參考文件一次載入。腳本的參數、輸出與錯誤處理以對應階段文件為準。

合併模式的完整驗證時機依 [整合與封存](closeout.md) 執行；rerun 集中在整合後、推送前，不在整合前多跑一輪。current／still-valid 未涵蓋所有共用程式與環境，不能代替整合驗證。
