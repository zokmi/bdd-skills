# 分階段工作流程

### 先決定驗證階段，再派工

進入本機實測前就讀 [整合與封存](closeout.md)〈7-0〉，確認本任務已指定的交付方式，不等到收尾才讀。每次派工明列「開發回饋／最終完整驗證」及情境清單：

依 [品質閘門](quality-gate.md) 決定每輪範圍。最終完整驗證指在最終候選版本跑完該輪選定範圍。小 issue 可用 TARGETED，FULL 條件適用時執行全套。

| 目前狀態 | 本輪驗證範圍與下一步 |
|----------|----------------------|
| 合併回 develop，尚未整合 | 只驗修正與受影響回歸，通過後提交並進入整合；不為取得 all pass 預先全跑。 |
| 交付方式未定 | 先驗修正與受影響回歸，通過後詢問交付方式；回答前不自行開完整驗證。 |
| 已選 feature 或明確只要實測報告 | 在功能工作區完成指定範圍的完整驗證。 |
| develop 候選整合已完成 | 在乾淨候選 commit 完整驗證一次，通過後推送同一 HEAD；推送後只核對遠端 SHA。 |

`rerun`／`no-record`、子代理自動分組與「測到全部通過」都不改變上述時機。開發回饋所需情境若恰好等於全部情境，照實執行並記範圍；不能省掉必要回歸，也不能把它當作尚未完成的整合驗收。若使用者明確要求整合前完整測試，依要求執行並說明整合後仍須驗證新版本。

### 實測範圍審核

每輪先依 [送審前準備](scenario-review.md#送審前依序派兩次唯讀準備任務) 依序派子代理選取範圍與產出清單，再固定候選版本、實際 diff、驗證階段、選測清單和略過理由。開始 UI／API／DB 實測或派實測子代理前，由未參與本輪選測或執行的子代理唯讀審核。提供 issue 原文與驗收條件的來源（無 issue 時提供原始需求）、基準與候選版本、未提交差異、實際選取的情境編號與路徑、相關 Feature、略過理由及預計驗證項目清單。新增或變更情境時，同一次派工可一併完成情境審核與實測範圍審核，分別記錄結論。

審核者逐條將本輪應驗的要求對到所選情境及實際斷言，並用 diff 檢查受影響的核心路徑、必要回歸及略過理由。開發中只複測部分需求時，列明延後驗證的條件與安排；最終驗證須覆蓋 issue 的全部驗收條件。回報 PASS 或 FAIL，附上需求與情境對照、缺漏或選入無關情境的依據。無法取得需求或 diff 時回報 BLOCKED。

漏選既有情境時補入清單。缺少可驗證的斷言時，新增或修改情境並完成 [情境審核](scenario-review.md)。主代理處理缺漏後，送更新清單複審，取得 PASS 才開始實測。需求、候選版本、diff、情境或清單變更時，先更新受影響的選測與驗證項目，再重新審核。條件與先前 PASS 完全相同的重試可引用該紀錄。無法派出獨立子代理時，保留測試計畫並回報審核阻塞。把候選版本、選測清單、審核者、對照與結論寫入報告〈實測範圍審核〉。

### 每輪實測的執行模式判定

初測、缺陷修正後複測、`rerun`、feature 完整驗證與整合後驗證，都在既有執行時機先判定一次；只產情境或整理既有報告而不實測時不派實測代理。此判定不額外增加測試輪次。

1. 主代理確認本輪情境、受測版本與環境安全，按模組、依賴、資料與瀏覽器衝突分組，不以情境數硬切；一組也必須分配給實測子代理，不得把有順序依賴的單一情境拆開湊組。
2. 每輪有實際測試時都必須由子代理執行。先讀 [子代理並行 BDD](parallel-bdd.md)，為每組建立派工契約並實際派工；可用名額少於組數時分批逐組派工，同一代理名額可在前一批完成後再次使用。使用者只說「測到全過」「複測」或「只給報告」也適用，不另問是否要用子代理。
3. 部分組衝突時採混合模式：衝突組由子代理序列執行，獨立組由子代理分批或並行執行。不可因只有一組、情境相依、暫時沒有空閒名額而改由主代理執行；等待名額並分批派工。平台沒有子代理派工能力，或使用者明確禁用子代理時，停止實測並回報阻塞及原因。不得為啟用並行改用假資料／繞過環境確認。
4. 執行前簡述所選模式及分組依據，寫入報告〈BDD 執行模式〉；派工後記錄實際代理與契約位置。子代理本身不遞迴派實測代理，只執行主代理分配範圍；需要再拆組時回報主代理。

情境獨立審核仍依原流程執行，不由執行該組的代理自行審核。無法派工時回報具體限制並停止實測，不假稱已派工或改由主代理執行。

序列派工時一併安排[提前準備測資](parallel-bdd.md#序列執行時提前準備測資)。同一名實測子代理可批次建立彼此獨立的前置資料，再依原順序執行各情境。

1. **確定範圍、版本與情境**：讀 [範圍、版本比對與情境撰寫](workflow-and-scenarios.md)。寫 `.feature` 前讀 [情境寫法](feature-guide.md)；使用模組時讀 [模組情境集](modules.md)。情境寫完後讀 [情境審核](scenario-review.md)。使用者只要情境時，在審核與未執行報告完成後停止。
2. **本機實測與修正**：需要執行時讀 [本機執行與複測](local-execution.md) 及 [報告與驗證紀錄](reporting.md)；worktree 另讀 [loopback 隔離](worktree-loopback.md)。逐情境保留證據，每輪先記錄結果與版本；失敗後修正、重啟並重測。
3. **報告**：需要報告時讀 [報告與驗證紀錄](reporting.md) 和 [報告範本](../assets/REPORT-template.md)。最終實測後依 [結果報告審核](closeout.md#共用-issue-交付最終完整驗證後自動執行) 的核對規則核對清單、報告與證據。使用者只要測試報告時不整合或更新 issue；若需封存，再讀下階段的封存步驟。
4. **整合與收尾**：依 [整合與封存](closeout.md) 確認模式、版本與完整驗證時機。每輪保存證據並完成截圖驗證審核後，依服務停止規則確認條件並釋放資源，回覆前核對程序與埠。遮罩、封存或清理時讀 [封存指引](archive.md)。

建立 `.bdd` 輸出前，依範圍指引呼叫內部 CLI 的 `gitignore` 子命令，自動驗證並補齊目標 repo 的忽略規則；切換 repo/worktree 或整合後重新檢查。衝突及已追蹤產物依 [版控分工](version-control.md) 處理。

各階段只讀當前需要的參考文件，不把整套參考文件一次載入。腳本的參數、輸出與錯誤處理以對應階段文件為準。

合併模式的完整驗證時機依 [整合與封存](closeout.md) 執行；rerun 集中在整合後、推送前，不在整合前多跑一輪。current／still-valid 未涵蓋所有共用程式與環境，不能代替整合驗證。
