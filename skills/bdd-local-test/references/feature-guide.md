# .feature 撰寫指引

## 情境範圍

情境文件描述模組對使用者或外部角色承諾的可觀察業務行為，涵蓋成功及適用的異常情況。每個情境交代角色、前置條件、操作或觸發事件與可觀察的業務結果；異動用來辨識受影響的流程及必要回歸，不是一項異動就新增一個情境。

- 使用者新增成功、必填錯誤、權限不足、重複送出等，屬於模組情境。
- 合作系統透過 API 提交訂單、重複請求被拒，以及到期排程發送通知、依業務規則重試失敗通知，也屬於模組情境。角色可以是外部系統或通知接收者；以請求、業務事件或到期條件描述觸發，不必虛構畫面或人工操作。
- 純重構、部署設定、SQL migration／repair、測試工具、文件調整等工程項目，記在驗證清單與報告，使用適合的靜態檢查、技術測試或部署驗證，不另寫成 `.feature`。
- 工程調整若影響對外業務行為，情境描述該業務觸發及結果，例如「升級後使用者仍可查閱既有資料」；migration 的資料保留、中止及 rollback 分支另做技術驗證，仍須符合資料安全規範。純背景索引維護、內部重試次數等實作細節另列技術驗證；需求明定的通知時限或重試結果則屬業務情境。
- `@UI`／`@API`／`@DB` 只表示驗證手段。API／DB 可支持操作結果的斷言，不因改了端點或資料表就新增技術情境。

判定時先問「這是否是角色可觀察、且需求承諾的業務結果？」是則維護模組情境；若只涉及實作或部署是否正確，則列技術驗證。可觀察包含回應、通知、狀態與可查閱資料，不限即時畫面；`@DB` 可驗證業務資料結果，斷言仍以業務規則為準。

## 逐項選擇驗證手段

編本輪清單時，先看「當」要求從哪個入口觸發，再把每個「那麼／而且」列為可判定的斷言。依觸發方式和可直接觀察結果的位置選手段，在〈預計驗證項目〉逐列寫下理由與證據。同一情境可以列數次，沿用原編號、角色及測資。

| 清單手段 | 判定與證據 |
| --- | --- |
| API 可驗 | 真實端點能觸發要求的行為並觀察結果。例如服務端欄位邊界、授權拒絕、重複提交、服務端排序。用符合需求的身分記錄回應欄位、錯誤或同一筆資料的查回結果。 |
| 必須 UI | 操作或預期發生在瀏覽器。例如點擊送出、欄位轉換、按鈕可見性、畫面提示、頁面導轉、列表刷新。以 Playwright CLI 執行該操作並核對可見結果。前端攔截提交時一併觀察請求是否送出。 |
| DB／事件／其他技術驗證 | 按需求從真實事件或排程觸發，核對通知、資料或其他約定結果。資料保留、中止與 rollback 等工程斷言採相應技術驗證。 |

例如「儲存後列表立即更新，重新查詢仍保留新金額」只從 UI 儲存一次。第一列用 UI 核對列表，第二列用 API 查回同一訂單 ID 核對金額。若需求同時要求「唯讀者看不到編輯鈕」及「直接送出修改會被拒絕」，前者以唯讀者登入看畫面，後者以同角色直接呼叫 API，並核對資料維持原狀。

沿用既有情境時應完成其明訂的入口、操作與預期。若認為原情境的 UI 步驟可改寫，先依需求確認並送情境變更審核。API 證據只計入實際驗到的斷言，漏做或阻塞的畫面操作按實況記錄。

## 檔頭

每個 `.feature` 檔開頭固定這幾行註解，讓沒參與開發的人也知道測什麼、從哪進去：

```gherkin
# language: zh-TW
# 範圍：<portal> <功能區塊>（模組 <portal>/<主路由>）
# 入口：<前端與路由／外部 API／事件來源與排程觸發條件>
# 標籤：@UI 瀏覽器操作｜@API 直接呼叫端點｜@DB 查資料庫驗證｜@已知缺陷 撰寫時已知會失敗｜@#<單號> 新增或修改此情境的單
# 情境編號 <前綴>-xx 供測試報告對照，前綴見 MODULE.md
```

檔頭描述的是模組，不是某一張單的分支差異；單號寫在各情境的 `@#<單號>` 標籤。

用情境層級的 `@core` 標記模組最重要的可用流程。新增或實質修改的情境依 [情境等級與必測範圍](scenario-priority.md) 另加一個 `@P0`／`@P1`／`@P2`。例如 `@SS-01 @#12345 @P1 @core @UI` 同時標示編號、單號、等級、主流程及手段。

`# language: zh-TW` 讓關鍵字用中文：`功能`、`背景`、`場景`、`場景大綱`、`例子`、
`假設`（Given）、`當`（When）、`那麼`（Then）、`而且`（And）、`但是`（But）。

## 結構

下例為 UI 流程。API／事件／排程情境改用實際角色、前置狀態與觸發條件；背景不要求登入或開啟頁面。模組依 [模組情境集](modules.md) 維護，已有模組者沿用其歸屬。

```gherkin
@<功能標籤>
功能: <功能名稱>
  身為<角色>
  我要<做什麼>
  以便<商業價值>

  背景:
    假設 我以具備「<權限名稱>」權限的帳號登入 <系統>
    而且 我在<頁面>選擇<前置條件>

  # ---------- <子區塊，例如：新增> ----------

  @<編號> @#<單號> @P1 @UI @DB
  場景: <一句話講清楚這個情境在驗什麼>
    當 <操作>
    那麼 <可觀察的結果>
    而且 <資料層的結果>
```

## 編號

- 每個模組一個 2–3 字母前綴，登記在該模組的 `MODULE.md`（`SS` 賽制管理、`MT` 場地時間表），情境依序 `SS-01`、`SS-02`…
- 新增情境用 `node bdd.mjs modules --next-id --module <模組>` 取號；用過的號碼不重用，刪除的記進 MODULE.md 的 `removed`。
- 編號一旦寫進報告與證據檔名就不要重排。並行分支撞號時的改號規則見 [模組情境集](modules.md)。

## 寫法要點

- **「那麼」必須可觀察、可判定**。寫畫面上的原文訊息、欄位值、API 回應欄位、資料表欄位值。
  「系統正常運作」「資料正確」這種無法判定的句子不要寫。
- **訊息原文照抄程式裡的字串**，這樣執行時才能直接比對；需求與程式不同時以需求為準並標 `@已知缺陷`。
- **一個情境只驗一件事**。多組輸入對應多組結果時用 `場景大綱` + `例子` 表格，不要複製貼上五個幾乎一樣的場景。
- **資料用具體值**：`BDD-地坪`、單價 `1350`、版本 `v2`，而不是「某個料號」「某個價格」。
- **API／DB 情境可以寫欄位名與端點名**（`BatchSaveData`、`tblItemCode.cStatus 為 9`），因為讀者就是要拿來驗的人；
  UI 情境則寫使用者看得到的文字。
- `@已知缺陷` 情境在最後一行加註解說明撰寫時看到的原因：

  ```gherkin
    # 撰寫時已知：驗證仍檢查舊欄位 CPart，任何輸入都會被判定「工程項目名稱為必填欄位」
  ```

## 覆蓋清單

每個功能區塊寫完後，對照這張清單檢查適用的業務行為分支；不適用的項目不必為湊齊清單新增情境：

- 成功路徑（含最小與最大合法值）
- 必填缺漏、格式錯誤、超過長度或範圍
- 權限不足（沒有該功能權限的帳號看不到按鈕、直接打 API 被拒）
- 空值、零值、空清單
- 重複資料、並行或重複送出
- 找不到資料（不存在的 ID）
- 與既有資料的互動：刪除有引用的資料、修改後舊資料的顯示、歷史快照是否被影響
- 操作觸發的業務資料限制：例如重複資料被拒絕、被引用資料無法刪除；純 SQL 約束與轉置結果另列技術驗證
