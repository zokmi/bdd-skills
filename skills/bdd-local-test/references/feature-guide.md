# .feature 撰寫指引

## 檔頭

每個 `.feature` 檔開頭固定這幾行註解，讓沒參與開發的人也知道測什麼、從哪進去：

```gherkin
# language: zh-TW
# 範圍：#<單號> 分支相對 <基準分支> 的「<功能區塊>」異動
# 入口：<哪個前端> <選單路徑>（<路由>）
# 標籤：@UI 瀏覽器操作｜@API 直接呼叫端點｜@DB 查資料庫驗證｜@已知缺陷 撰寫時已知會失敗
# 情境編號 <前綴>-xx 供測試報告對照
```

`# language: zh-TW` 讓關鍵字用中文：`功能`、`背景`、`場景`、`場景大綱`、`例子`、
`假設`（Given）、`當`（When）、`那麼`（Then）、`而且`（And）、`但是`（But）。

## 結構

```gherkin
@<功能標籤>
功能: <功能名稱>
  身為<角色>
  我要<做什麼>
  以便<商業價值>

  背景:
    假設 我以具備「<權限名稱>」權限的帳號登入 <系統>
    而且 我在<頁面>選擇<前置條件>

  # ---------- <子區塊，例如：新增> ----------

  @<編號> @UI @DB
  場景: <一句話講清楚這個情境在驗什麼>
    當 <操作>
    那麼 <可觀察的結果>
    而且 <資料層的結果>
```

## 編號

- 每個功能區塊一個 2–3 字母前綴（`IC` 料號、`PV` 價格版本、`RQ` 需求），情境依序 `IC-01`、`IC-02`…
- 編號一旦寫進報告與證據檔名就不要重排；新增情境往後接號，刪除的留空號。

## 寫法要點

- **「那麼」必須可觀察、可判定**。寫畫面上的原文訊息、欄位值、API 回應欄位、資料表欄位值。
  「系統正常運作」「資料正確」這種無法判定的句子不要寫。
- **訊息原文照抄程式裡的字串**，這樣執行時才能直接比對；需求與程式不同時以需求為準並標 `@已知缺陷`。
- **一個情境只驗一件事**。多組輸入對應多組結果時用 `場景大綱` + `例子` 表格，不要複製貼上五個幾乎一樣的場景。
- **資料用具體值**：`BDD-地坪`、單價 `1350`、版本 `v2`，而不是「某個料號」「某個價格」。
- **API／DB 情境可以寫欄位名與端點名**（`BatchSaveData`、`tblItemCode.cStatus 為 9`），因為讀者就是要拿來驗的人；
  UI 情境則寫使用者看得到的文字。
- `@已知缺陷` 情境在最後一行加註解說明撰寫時看到的原因：

  ```gherkin
    # 撰寫時已知：驗證仍檢查舊欄位 CPart，任何輸入都會被判定「工程項目名稱為必填欄位」
  ```

## 覆蓋清單

每個功能區塊寫完後，對照這張清單看有沒有漏：

- 成功路徑（含最小與最大合法值）
- 必填缺漏、格式錯誤、超過長度或範圍
- 權限不足（沒有該功能權限的帳號看不到按鈕、直接打 API 被拒）
- 空值、零值、空清單
- 重複資料、並行或重複送出
- 找不到資料（不存在的 ID）
- 與既有資料的互動：刪除有引用的資料、修改後舊資料的顯示、歷史快照是否被影響
- 資料約束與轉置（有 SQL 異動時）：唯一性、外鍵、NULL 規則、轉置後筆數與對應是否正確
